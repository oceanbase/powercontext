# Codex Desktop handoff qualification

The default target registry includes a detectable Codex Desktop adapter even before it has launch qualification. `TargetCatalog.list()` marks it unavailable for native preflight and offers manual delivery; `TargetCatalog.diagnose()` can run read-only detection without exposing the internal configuration key. Host routes must explicitly expose that diagnostic operation if the product needs to display its result. Native preflight and launch require real acceptance evidence for the exact application and CLI version and the shared receiver prompt builder. `createCodexDesktopRuntime` takes the embedded CLI path, actual Desktop `CODEX_HOME`, Host delivery root, and the Host's persistent 32-byte generation key. Optional setup inputs are an absolute PowerContext executable and the intended non-secret Server URL. The generation key is used for keyed configuration fingerprints and is never emitted by the adapter.

The runtime queries the embedded app-server without creating a thread: `plugin/installed`, `hooks/list`, `config/read`, `configRequirements/read`, and `mcpServerStatus/list`. It checks the installed and enabled PowerContext plugin and required receiver tools. In the target directory it requires the enabled, trusted PowerContext SessionStart and PreToolUse hooks, and uses the installed plugin's own settings, credentials and Scope resolver for a new session. It compares the effective MCP endpoint and authorization configuration against the hook endpoint, and obtains the Server identity through the existing read-only identity operation. A changed target Scope, credential, hook or configuration changes the keyed generation and invalidates the preflight. The same persistent Host key reproduces the generation after restart.

For the qualified app version the runtime reads the saved local Desktop permission selection and checks app-server managed restrictions. The version-qualified mappings are `read-only` to `:read-only`, `auto` and `guardian-approvals` to `:workspace`, and `full-access` to `:danger-full-access`. Unknown, ambiguous or unsupported selections fail closed. It runs the embedded `codex sandbox` with that profile and managed configuration to hash a temporary private file in the delivery store; immediately before launch it hashes the exact package through that sandbox and compares the persisted SHA-256. Host readability alone is not sufficient.

The mapping is based on the inspected application build, not a public deep-link permission parameter. The actual application can have in-memory or per-session permission choices and environment variables that differ from the DSH process. Verify the chosen profile and effective plugin environment in a real new Desktop chat before qualification; do not infer them from the CLI probe alone. Revalidate after changing the app version, selected permissions, managed policy, `CODEX_HOME`, plugin, connection, hooks or workspace. Custom Desktop permission selections are not yet qualified.

Installation is performed only through the existing consented preflight and `powercontext setup codex`. With an explicit `source`, supply the marketplace root: for this repository that is the repository root containing `.agents/plugins/marketplace.json`, not the plugin directory. With no `source`, the CLI currently uses its remote `oceanbase/powercontext` marketplace at `master`; this requires network access and is not an offline bundled installation. The embedded CLI directory is prepended to PATH for Desktop-only installations. Setup completion still requires the user to restart or verify the Desktop target; interrupted or failed setup is indeterminate because it may have partially written configuration.

## Real-host acceptance

Coordinate with the local user and preserve existing sessions and drafts. Use a disposable project and a real PowerContext Server; do not edit application-private databases or submit the receiver prompt automatically.

1. Record app build, embedded CLI version, actual `codex://` system handler, Desktop `CODEX_HOME`, selected profile and target configuration. Verify that the app-server and new Desktop chat use the same plugin, credentials, environment and managed policy. Confirm hook trust and the receiver tools in the actual Desktop session.
2. Verify the canonical directory, target Server and Scope before the new-session hook injects context. Check a conflicting binding and a changed configuration between preflight and launch; neither may silently rebind.
3. Verify the selected Desktop sandbox reads the exact persisted package and SHA-256. A denied or modified package must stop automatic delivery. Confirm a profile change invalidates preflight.
4. With a user-approved launch, check that `codex://threads/new` opens a new local chat in the intended directory, with the complete prompt in the composer and **not sent**. Check non-ASCII paths and preservation of the source session and draft.
5. Only after the user explicitly sends the draft, verify the real receiver reads the exact package, invokes Continue and ACK, and the existing receipt verifier accepts the intended attempt, Server, Scope and identity. Check restart recovery and stale or wrong receipts. An OS open is not receiver acceptance.

The official [deep-link reference](https://learn.chatgpt.com/docs/reference/commands#deep-links) documents `codex://threads/new` with `path` and `prompt`, and says the prompt remains unsent. The [hook documentation](https://learn.chatgpt.com/docs/hooks) requires trust for non-managed hooks. Documentation and isolated probes do not establish that an installed app passed these real-host checks.
