## Executed checks

- Real Web page boot: `powercontext-dsh` appeared in `window.__DSH_BOOT__.entries`; sidebar state `ready`
  (`Connected`); panel `role=dialog`, visible, focus inside, no launch token or Bearer value shown.
- Real Web collapse: sidebar collapse produced `pc-trigger-rail` at 36x36; the 394px panel remained visible and
  focused.
- Real Web keyboard: Enter opened the panel and focused `Refresh status`; Escape closed it and restored focus to
  the trigger.
- Real Web dark palette: `body[data-ds-dark-theme]` produced body `rgb(21, 21, 23)` and panel
  `rgba(48, 49, 54, 0.64)` with light text, using DSH tokens.
- Real Web unauthenticated request: `GET /powercontext/status` without the DSH cookie returned `401` with
  `dsh_authentication_required`.
- Real Web unconfigured owner-local: a second Web host without `POWERCONTEXT_DSH_OWNER_LOCAL` returned `403
  owner_local_unverified`; the sidebar rendered gray `Not configured` and offered guidance. The same result occurred
  when a Web profile was booted with the Desktop-bundled Electron CLI, proving that the Electron engine alone does
  not grant Desktop authority.
- Real session switch: the test-only `session-fixture` Host plugin created genuine DSH `session-9` and `session-10`
  sessions in different workspaces. Selecting each through the host's persisted current-session entry produced
  `session-9`/`scp_3pfse0c26fsrh3msfxtaqd620x` and `session-10`/`scp_2hhmevg0m3c8pkzz5by2xcarsb`; the bridge received
  both exact `session_id` selectors. Selection used the host's persisted current-session entry plus a page reload.
  Late-response isolation is covered by controller unit tests, not by this two-session real-host check.
- Real Web offline recovery: stopping the PowerContext Server produced a red `connection_refused` state; restarting
  it returned the same live page to green `Connected` without reload.
- Desktop bundled runtime: installed the plugin into an isolated `desktop` profile with the DMG's own
  `runtime/cli/bin/dsh`, booted that profile through the shipped 0.2.2-rc.1 runtime, and repeated the real Web
  harness. The bridge reported `deployment.mode=desktop`, `owner_local=automatic`, `kind=local`; sidebar/panel,
  focus, Escape, collapsed rail, keyboard, dark palette, and 401 checks passed.
- Desktop Electron shell: the parent launched the **mounted packaged** 0.2.2-rc.1 app (not a copied app) with
  `CFFIXED_USER_HOME=/tmp/dsh-desktop-acceptance/home`, `DSH_HOME=/tmp/dsh-host/desktop-home`, and CDP on 9224.
  The isolated Desktop profile dependency was `file:/tmp/dsh-release/pc-plugin/powercontext-dsh-0.1.0.tgz`; its
  `node_modules/powercontext-dsh` was a real directory (not the source symlink). The actual `dsh-app://app/` window
  booted that `powercontext-dsh`, reported green `Connected`, and exposed
  `DSH Desktop · automatic desktop signal`. Keyboard Enter/Escape, dialog focus, collapsed rail, and the real
  Settings → Appearance dark/light switch were asserted by `web-acceptance.mjs` with `DSH_EXISTING_TARGET=1`.
  The personal `desktop/settings.json`, Cookies, and local storage retained pre-launch timestamps. The isolated
  profile's default workspace resolved under `Documents`; status read only and no personal file was edited.
- Release tarball install: `powercontext-dsh-0.1.0.tgz` (SHA-256 above) was removed/reinstalled as a file
  dependency in the isolated Desktop profile and independently installed into a fresh DSH Web profile. Both real
  harnesses exited 0 with green status and the booted `powercontext-dsh` client entry; the Desktop profile shows a
  real `node_modules/powercontext-dsh` directory, not a source link.
- Packaged client asset route: the active real Web host served
  `/plugins/powercontext-dsh/assets/powercontext.svg` with HTTP 200 and `image/svg+xml` content.
- Real setup: `powercontext setup dsh --source . --profile web --server-url ... --dsh-command <DSH 0.2.2-rc.1>`
  returned `ok=true` with `browser_client=present`, registration present, and Server readiness ok.
- Headless/optional: `registerStatusBridge` is skipped when the optional `webServer`/`connection` services are
  absent; unit coverage confirms no route and no effect are registered. Full plugin unit, e2e, and package tests
  run separately in the PR report.
