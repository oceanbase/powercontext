# Gateway 追问场景的记忆召回评测

用户和 Agent 连续对话时，经常只说“继续”或“按上次那个来”。Gateway 如果只拿最后一句去查，就可能不知道该找哪条历史约定。如果当前对话已经给足信息，再查一次也可能带进无关内容。这里的**召回**是指从 PowerContext 查找过去保存的信息，并把找到的内容交给负责回答或执行任务的主模型。

例如，“继续”可以发生在两种不同的场景。一种是用户要求按上次约定修复登录超时，本轮对话只提到有一条旧规则。规则的具体内容“保留原异常类型”存在 PowerContext 里，Agent 执行前需要把它找回来。另一种是修复和测试已经做完，双方明确下一步只运行 `git diff --check`，这时当前对话已经提供了下一步所需的信息。

这份评测分别检查召回是否正确、程序能否读懂模型的判断，以及这次额外的判断能否复用上游已缓存的会话前文。

## 怎么测

### 比较开启和关闭时，主模型实际收到什么

我们在隔离的 PowerContext 实例里预存了六条规则，例如登录超时要保留原异常类型。两组使用同一个 DeepSeek Flash Chat 模型、同一批 24 条构造对话和同一份记忆。关闭时沿用最后一句话检索的行为。开启时，Gateway 先用一次辅助模型调用，根据对话判断要不要查记忆，并在需要时给出检索词。每组每条案例跑三次，共 72 次请求。这三次是重复观测，分别用于观察首次运行和缓存预热后的表现。

四类案例各六条。模糊追问需要用前文补齐任务。明确任务用当前对话就可以执行。切换任务时要跟上新主题。工具返回结果时，Agent 继续已有任务。每条事先标注应不应该查、该找到哪条记忆。评测查看 Gateway 是否实际发起查询，以及最终交给主模型的内容。需要记忆时，应只传入指定记忆。无需记忆时，应跳过查询并且不传入记忆。[标注样本](../../../gateway/crates/pc-gateway-app/tests/fixtures/context_disambiguation.json) · [逐次结果](results.json)

### 单独验证模型返回的判断能不能读

辅助模型要返回一个简短的判断，例如 `{"recall":true,"query":"登录超时的兼容规则"}`。其中 `recall` 表示要不要查，`query` 是检索词。如果模型在答案之后继续写说明，Gateway 可能无法读出判断，只能回到原来的最后一句话。我们固定同一份两步指令，24 条样本各跑两次。一组只在指令里要求 JSON，另一组还通过 DeepSeek Chat 的 API 参数要求返回一个 JSON 对象。这项功能叫 **JSON 模式**。[评测入口](evaluate.py) · [JSON 模式实测记录](follow-up-results.json)

### 验证上一轮的主请求能不能帮助下一轮消歧

同一段对话前文可能随请求反复发送。**前缀缓存（prefix cache）**是上游模型服务保存对这段相同开头的处理结果，后续请求带着相同前文时可以复用，减少重复处理。

我们用本地提交 `97ab095e9` 跑了三个独立会话。每组先发一次主模型请求，只让上游看到原始会话。下一轮保留相同前文，追加刚才的真实回复和一条追问，触发辅助模型调用。我们核对发给上游的共有消息完全一致。每组另有一个等长、此前没发给上游的会话做对照。最后读取 DeepSeek 报告的缓存 token 数，也就是它实际从缓存复用的输入量。[跨轮缓存实测记录](follow-up-results.json)

## 测到了什么

### Agent 更常拿到任务需要的旧约定

执行登录超时修复的三个观测里，关闭消歧时，每次都只拿“继续”去查，三次都没把旧规则交给主模型。开启后，检索词补上了“此前约定的登录超时兼容规则”，**三次都把“保留原异常类型”交给了主模型**。在另一个只需要运行 `git diff --check` 的场景里，开启后也三次都跳过了查询。

| 72 次请求中的表现 | 关闭消歧 | 开启消歧 |
| --- | --- | --- |
| 需要记忆，且只把标注的记忆交给主模型 | 21/36（58.3%） | 31/36（86.1%） |
| 无需记忆，且跳过查询、没有添加记忆 | 18/36（50.0%） | 32/36（88.9%） |
| 合计符合标注 | 39/72（54.2%） | 63/72（87.5%） |
| 95% 的请求在该时间内完成（P95） | 1.19 秒 | 2.44 秒 |
| 72 次请求的估算模型费用 | $0.00804 | $0.01107（+37.6%） |

合计多了 **24 次符合标注的请求**。其中 10 次是多拿到正确记忆，14 次是避免了多余查询。也有变差的例子。一次从 HTTP 客户端设置切到登录超时后，检索词还带着旧主题，结果漏掉了目标规则。费用按 DeepSeek 报告的输入和输出量估算，包含辅助调用。[逐次结果](results.json)

### JSON 模式让更多判断能被用上

固定同一提示词后，Gateway 能读懂的辅助输出从 **31/36 增到 34/36**，目标记忆命中从 **19/24 增到 23/24**。有两次输出仍需回退。上表的时延和费用来自功能开关对照，JSON 模式的结果来自另一组实验。[JSON 模式实测记录](follow-up-results.json)

### 上一轮主请求可以为下一轮消歧提供缓存

有上一轮主请求的三次消歧调用，在 DeepSeek Chat 上每次都命中 **1,536 个缓存 token**，约占辅助请求输入的 **83%**。三次此前没发送过对应前文的对照，命中都为 **0**。这组实测表明，在 DeepSeek Chat 上，两个用途不同的请求可以复用相同的长前文。实际命中取决于模型服务、共有前文的长度和缓存状态。[跨轮缓存实测记录](follow-up-results.json)

### 是否值得多一次模型调用，要看完整任务

这次确认的是，主模型更常在第一次执行前拿到正确约束。登录超时任务是否真的保留了原异常、用户是否少纠正一轮、完成整个任务是否更省，仍待端到端验证。完整评测应让 Agent 执行同一批任务，比较最终通过率、用户纠正轮次，以及把主模型和辅助调用都加进去后的总费用和耗时。按本次单请求的均摊费用粗算，如果两组任务成功率相同，且这些费用能代表完整任务，开启消歧后主请求数减少约 **27%** 时费用持平。
