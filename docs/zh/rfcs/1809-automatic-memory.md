# 摘要

本 RFC 引入 `automatic-memory` family，将每条可独立维护的记忆表示为一个 Artifact。Scope 负责归属，每条记忆
拥有自己的身份、版本、证据和生命周期。抽取先生成候选，再通过有界检索找到同 Scope 内有权读取的相关当前记忆，
协调新建、修订、归并与冲突。检索遵守前置 RFC #1803 的无 JOIN 召回与当前投影契约。现有部署通过独立工具停服升级，
迁移完整条目历史并保留旧精确引用；新 Runtime 不承担在线搬运和双写。

# 动机

## 记忆集合重复承担了 Scope 与 Artifact 的职责

[RFC 0014](0014_memory_layer_design.md) 中的 Memory Artifact 保存完整条目目录，每个成员引用不可变的 entry
version。修改一条记忆后，还要提交集合 revision。[RFC 1345](1345_scope_organization_and_agent_integration.md)
引入 Scope 后，记忆仍沿用唯一活跃集合。一条事实因此同时具有集合身份、entry 身份和两层版本。

Scope 已经承担归属与组织，Artifact 已经提供身份、历史、证据、授权和标签。将事实直接表达为 Artifact，可以统一
各类制品的维护方式，减少 Memory 专有的版本和引用规则。

## 单条修改仍产生全量目录历史

当前实现支持 entry 修订、历史读取、容量限制、可选 compact，以及按变化条目更新检索投影。正文与向量可以增量更新，
但每次有效修改仍需构造并保存全量 manifest。长期写入会持续累积未变化条目的目录副本；修改不同条目的任务也依赖
同一个集合 head。

容量限制可以约束单个集合大小，但不会改变版本化单位。独立记忆使历史增长对应实际发生变化的事实。

## 抽取上下文随活跃记忆增长

当前内置抽取把所选 Memory head 的全部活跃 entry 交给模型，能够修订过去 Source window 产生的记忆。随着记忆
积累，这种上下文组织方式持续增加输入成本，也缺少候选生成后的独立相关检索与完整的归并、冲突处理边界。

抽取应当围绕本次候选选择相关记忆。单独增加 entry 替换接口，仍无法解决上下文规模和跨记忆协调的问题。

# 使用说明

## 每条记忆独立维护

同一 Scope 可以有“生产发布需要负责人审批”和“默认部署区域为华东”两条 Automatic Memory。补充“发布还需要
安全检查”时，只推进第一条记忆的版本，第二条保持不变。读取旧精确引用仍返回原文，搜索返回当前可检索版本。

Automatic Memory 可以由 Source 自动抽取，也可以由有权限的调用方手工写入。`automatic` 不限制生产入口。

## 新输入与相关记忆协调

处理新的 Source 时，先生成候选，再检索同 Scope、合法读取范围中的相关当前记忆。抽取可以创建新事实，补充或纠正
已有事实，提出多条记忆的归并，或在没有新内容和证据时不写入。无法判断适用条件或先后关系的矛盾保留为未决冲突。

相似度用于选择相关对象，不能证明两条事实应当合并。归并必须保留有效证据和适用条件，并遵守授权与评审规则。
一次有界检索不承诺发现全部重复；未完成的协调与未决冲突应当能够继续处理。

## 生命周期保留历史

遗忘使记忆退出默认检索，之后可以显式恢复同一身份。恢复旧内容会生成新的当前版本，并保留恢复来源，历史版本
保持不可变。退休的身份不能通过普通恢复重新启用；采用其内容需要新身份并保留来源。

归并后，被停用记忆的旧引用仍返回当时的正文。历史正文读取不依赖向量服务，恢复后的当前搜索遵守公共检索契约。

## 现有部署停服升级

升级需要维护窗口、一致备份和独立迁移工具。工具完成历史转换及校验后才允许新版本开放业务。已经消费的 Source
不会重新抽取，已有 Handoff、Experience 等制品中的精确历史引用继续可用。

旧 `memory` 名称可在明确支持的操作中兼容到 `automatic-memory`。旧集合引用仍表示集合，不能直接当作某一条新
记忆；依赖旧集合语义且没有明确兼容规则的调用方需要升级。

# 参考级说明

## 领域边界

- Scope 是记忆的归属与访问边界，`automatic-memory` 是独立记忆的 Family。每条记忆使用普通 Artifact 身份与版本，
  不再维护全 Scope 的版本化 manifest。
- 正文、直接证据或生命周期的有效变化只增加受影响记忆的历史。归并与恢复必须保留精确来源，历史证据不能按迁移
  时的规则重新解释。
- Source 消费继续由 Scope 内的处理绑定负责，不为每条记忆引入独立消费进度。输入进度的推进不能丢失已接受的工作。
- 当前记忆容量和历史保留分别治理。达到容量限制时，仍应允许不增加容量的修订及减量补救，不能通过丢弃历史满足限额。

这些变化替代 RFC 0014、0019 中的集合与 entry 专用版本模型，调整 RFC 1345 的唯一活跃 Memory 集合约束，以及
RFC 1718 的集合容量单位；继续沿用 RFC 1549 的统一 Artifact 能力和 RFC 1652 的证据、评审与生命周期边界。

## 抽取与写入约束

候选生成、相关检索和协调均应有明确预算，不把 Scope 中全部活跃记忆作为默认模型上下文。缺少向量能力的部署仍需
采用有界检索。新建、修订、归并、不写入和未决冲突应有明确结果；预算耗尽不能当作没有新记忆。

普通新建和修订沿用抽取授权与写入门禁。语义归并默认逐次评审、默认不自动执行。本提案对 RFC 1652 作有限调整：
Scope 管理者可以对同一对象、同一适用范围、内容兼容且完整保留证据的归并给予有限预授权。强制评审、未决冲突、
超出授权范围及不可逆退休仍需逐次处理。模型判断不能代替授权，显式调用也不能绕过强制评审。

并发写入与重试不得覆盖后续变更、重复创建同一请求的结果，或发布只完成一部分的归并。协调所依据的内容、证据和
权限发生变化时，应重新确认写入资格。具体并发机制不由本提案规定。

## 公共检索依赖

[RFC #1803](https://github.com/oceanbase/powercontext/pull/1803) 是本提案的前置契约。Automatic Memory 维护
自己的当前检索数据，可以采用宽表或独立的全文、向量投影。召回语句不使用业务表 JOIN；标签、状态等资格条件
参与候选选择。候选确定后，可以按精确引用独立批量读取正文，与召回保持一致状态，不能在补齐阶段重新过滤候选。

当前投影的更新、重建与可见性遵守 #1803。本提案不重新定义公共检索规则，也不承担其他 Family 的领域模型改造。

## 兼容与迁移承诺

公共 API 及其消费者改用单条 Artifact 身份，不再假定同 Scope 的所有记忆共用集合引用。旧名称兼容集中处理，并根据
操作语义区分当前 Family 选择与精确历史引用；鉴权和执行必须使用同一身份解释。名称兼容不承诺旧集合接口等价。

迁移由显式运行的独立工具承担。服务二进制不保留在线搬运、双写和追平流程；承诺支持的旧版本仍需有可获得的工具
和升级路径。迁移期间停止旧写入；失败或未完成校验时，不得开放新版业务。

迁移范围包括全部条目的正文、证据与生命周期历史，以及原有精确引用、访问控制、标签和处理水位。保留旧集合快照，
不改写已有制品中的引用，不改变退休条目的不可直接恢复语义，也不重新抽取已消费的 Source。迁移应支持安全重试，
缺失或无法解释的历史必须在切换前解决，不能静默丢弃。

新版开始接受写入后，旧集合不会继续同步。部署降级需要独立的逆迁移安排，不能等同于恢复某条记忆的历史内容。

# 缺点

- 身份、接口及消费者需要升级，完整历史转换带来停服时间和额外存储成本。
- 保留旧历史与精确引用仍有长期兼容负担；停止写入全量 manifest 不会立即释放已有历史占用。
- 有界检索可能漏掉相关记忆，语义归并可能丢失限定条件，需要证据、评审和后续维护。
- 独立记忆仍需处理跨记忆一致性、并发协调和容量治理，不能仅将 entry 换名后完成改造。

# 设计理由与替代方案

**独立 Artifact。** 复用 Scope 的归属和 Artifact 的身份、历史与治理能力，使每条事实成为维护单位，与其他制品一致。

**沿用 `memory` family。** 能减少命名变化，但同一 Family 将同时承载集合与单条语义，增加能力发现、接口和历史读取
的歧义。新 Family 明确区分两种模型，旧名称在受控入口兼容。

**增量 manifest 或多个小集合。** 可以降低目录成本或限制单集合规模，但仍保留集合版本、entry 专用引用和跨集合协调。
集合快照不是本提案选择的长期维护单位。

**仅迁当前内容。** 可以缩短升级时间，但新身份的历史只能从导入开始。完整历史迁移能保持每条记忆的正文、证据与
生命周期连续性，因此接受更多离线迁移工作。

**在线迁移。** 可以减少停服，但支持历史版本直接升级的二进制产品必须持续携带或调用在线搬运与切换能力。
独立离线工具将这项长期维护责任移出正常服务运行路径。

**维持现状。** 可继续用容量和 compact 限制集合大小，但两层版本、全量目录历史和专用引用规则仍会保留。

# 未解决问题

- 旧集合接口、精确历史读取和迁移工具的支持版本范围，以及公共协议的升级边界。
- 当前记忆容量与历史保留的配置政策，以及多旧容器合并后超限的处置政策。
- 未决冲突和归并评审面向用户的处理方式，以及不能自动补偿的下游影响如何表达。

物理删除、跨 Scope 自动归并、在线升级和隐式全 Scope 快照回滚不属于当前范围。具体表结构、接口形式、并发机制与
迁移步骤由后续实现设计确定。

# 后续可能性

- 有界后台维护可发现即时抽取未召回的近重复与冲突，继续沿用证据与评审边界。
- 历史保留、物理清理与显式 Scope 导出可单独定义，不在每次单条写入时重新引入全量目录。
- 商业版可提供在线升级，并设置必须完成迁移后才能继续升级的栅栏版本，使后续二进制能够移除历史在线迁移代码。
  栅栏版本及其工具须在承诺的支持期内持续可获得；安装该版本本身不代表迁移已经完成。
