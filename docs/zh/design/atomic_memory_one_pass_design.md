# 系统设计：原子记忆单次整理（One-pass）

| 项 | 内容 |
| --- | --- |
| 特性类型 | 原子记忆处理模式；配置网关回连的 Server 默认开启，其余场景保持逐候选默认 |
| 对外契约 | 不新增 HTTP API，不改 OpenAPI，不改持久化格式，不新增提示词 key |
| 新增配置 | 一个 Server 运行时配置项，选择原子记忆处理模式 |
| 文档状态 | 已实现，评测结果见 §6 |
| Language | 中文（技术术语保留英文原文） |

---

## 0. 一句话概括

原子记忆现在的处理方式是：先对 Source 窗口抽取候选，再对每条候选单独召回相关记忆、单独调用模型对账。
单次整理把这两件事放进同一段对话的两步里：第 1 步列出要写的记忆（各自包含哪些事实）和检索词，Core 按检索词召回已有记忆，
第 2 步在同一对话里直接给出最终的 create / revise / merge / noop 操作。第 2 步复用第 1 步的输入前缀，
可以命中模型服务的前缀缓存，因此不再为每条候选重复发送整段 Source。

它作为可选模式提供：在两个评测集上，成本是现有流程的 20%–31%，存储条数与现有流程接近，
编码场景的事实覆盖度持平，对话场景的问答准确率不低于现有流程（见 §6）。配置网关前缀抽取回连地址的 Server 默认使用单次整理，显式配置仍优先；SDK 与未配置网关回连的 Server 保持逐候选默认。全面替换默认模式的条件见 §8。

## 1. 约束

| # | 约束 | 保证方式 |
| --- | --- | --- |
| C1 | 发布路径不变：写入仍经过 `AtomicMemoryWindowWorkset`、写入闸门、`_publish` | 单次整理只替换 `_prepare` 内的候选生成与对账，产出同一个 workset |
| C2 | 溯源不变：每条发布的记忆仍带正确的 `sources` | 第 2 步的每个操作给出 `evidence_ids`，Core 校验后按现有方式计算 `sources` |
| C3 | 校验与读依赖不变 | 每个 revise / merge 转换为 `AtomicMemoryReconciliationOutput` 后由 `workset.apply()` 校验；展示过的已有记忆全部记入 workset 的读依赖，发布时照常做冲突检查 |
| C4 | 提示词配置不分裂：用户仍只维护 `atomic_memory.extract` 与 `atomic_memory.reconcile` | 流程指令是代码常量；两个 key 的现有配置嵌入其中（§4） |
| C5 | 显式模式优先，默认值按部署配置选择 | 网关回连已配置且模式未指定的 Server 使用单次整理；其余默认与显式逐候选模式保留原流程 |

## 2. 现有流程（master）

`AtomicMemorySourceWindowProcessor._prepare`（`builtin/runtime/atomic_memory_processing.py`）：

1. 把窗口内可生成的 Source 投影为 `AtomicMemoryEvidence`，`evidence_id` 为 `source:{journal_position}`。
2. `pipeline.extract(AtomicMemoryExtractionInput)` 抽取候选，每条候选至少引用一个 `evidence_id`。
3. 对每条候选：与窗口内已加入 workset 的条目比较，再按 `related_page_size` 分页召回已有记忆；
   每批最多 `comparison_batch_size` 个相关条目，调用一次 `pipeline.reconciler.generate()`，
   用 `workset.apply()` 应用 create / revise / merge / noop。
4. 返回 workset，由 `_inspect_decisions` 与 `_publish` 完成写入闸门与发布。

成本集中在第 3 步：每次对账都重新发送候选证据和相关条目，候选正文在抽取与对账中各输出一次。

## 3. 单次整理流程

### 3.1 对话的三步

```
第 1 步  [流程指令 + 抽取规则] + [证据] ──▶ 模型 ──▶ {"items":[{"memory","details","query"}, ...]}   (≤30 项)
         Core 用每个 query 召回已有记忆，分配本轮标签 M1, M2, ...
第 2 步  同一前缀 + 第 1 步回复 + [已有记忆列表] ──▶ 模型 ──▶ {"operations":[...]}
第 3 步  仅当某条 create 的正文召回到第 2 步没展示过的记忆时：
         同一前缀 + 第 2 步回复 + [这些 create 与各自的未展示记忆] ──▶ 模型 ──▶ {"operations":[...]}
应用     每一步的操作经 workset.apply() 进入现有发布路径
```

- **第 1 步按记忆列，不按事实列。** 每一项是一条要写的记忆（一个主体的一个话题，粒度按抽取规则对候选的要求），
  带一个 `details` 列表逐条点名这条记忆必须包含的事实，以及一个检索词。第 2 步对每一项给出一个操作。
  模型在第 2 步会照着第 1 步的清单逐项写：按事实逐条列出时，每个事实都成为一条独立记忆，存储条数是现有流程的
  3 倍；只列话题而不点名事实时，事实会被遗漏（§6.3）。
- **第 1 步只负责检索。** 指令明确说明：第 1 步只是为了找出需要比对的已有记忆，拿不准的项和事实也要列上，
  保留与否由第 2 步决定。评测中去掉这一说明后，模型会随机返回空列表，整轮不写入（§6.3）。
- **第 1 步为空时仍进入第 2 步**，此时展示的已有记忆为空。代价是一次短调用，避免第 1 步误判导致整轮漏写。
- **后一步续接前一步。** 每一步的请求都是上一步的请求加上模型回复和一条新消息，指令与此前的消息逐字相同，
  可由模型服务的前缀缓存命中。这一点不依赖网关。
- **标签而非 ID。** 已有记忆以 M1、M2… 展示，Core 负责映射回 workset key。
- **回复不合规则时在同一步内纠正。** 每一步的回复先应用到 workset 的副本上；标签未知、缺少证据、
  时间限定词丢失等规则被违反时，规则名称返回给模型重答（次数受现有 `max_requests` 限制），副本丢弃。
  纠正次数用尽后本窗口失败，不发布部分结果。回复的顶层只接受该步规定的字段：换了字段名的回复
  （例如用 `candidates` 代替 `operations`）同样返回给模型重答，不会被当作"没有任何操作"而消费掉窗口。
- **第 2 步的操作不少于第 1 步的项数。** 操作不带第 1 步的编号，Core 只能按数量核对：
  第 1 步列出的项（按检索词去重、至多 30 项）多于第 2 步的操作时，回复按不合规则处理，纠正说明给出两边的数量。
  不值得保留的项以不带目标的 noop 作答，同样算作对这一项的决定。第 1 步为空时，空的操作列表照常接受。

### 3.2 证据与溯源

第 1 步的证据沿用 `AtomicMemoryExtractionInput` 的渲染方式（含输入编码），每段证据带 `evidence_id`。
第 2 步的 create / revise / merge 给出 `evidence_ids`，Core 校验其属于本窗口证据，再按现有方式构造工作条目：
`evidence=selected`、`sources=tuple(item.source_ref for item in selected)`。缺省时：

- 窗口只有一个 Source：补为该 Source；
- 只合并已有记忆、不含新事实的 merge：以被合并记忆的已发布内容作为依据；
- 其余情况按无效回复处理。

create 的内容按抽取候选的同一套规则校验（`validate_extraction_output`：kind、正文、引用的证据、时间限定词）。

### 3.3 应用到 workset

| 操作 | workset 处理 |
| --- | --- |
| create | 以操作内容新建条目，直接保留 |
| revise | 以操作内容新建 proposal，`related` 为唯一目标条目，按 `revise` 应用 |
| merge | 以操作内容新建 proposal，`related` 为全部目标条目，按 `merge` 应用 |
| noop | 不新增条目，目标记忆不变 |

revise / merge 的 `compared_ids` 与 `target_ids` 都取目标条目，`reason` 由模型给出；
`validate_reconciliation_decision` 的规则原样生效。内容与目标完全相同的 revise
（`RedundantAtomicMemoryRevisionError`）按 noop 处理。

**一次回复对同一条已有记忆最多写一次。** 操作按顺序应用，revise / merge 的内容整体替换目标记忆的正文；
模型写每个操作时依据的都是展示给它的原始正文，因此同一次回复里第二个写同一条记忆的操作会覆盖第一个写入的事实。
Core 在应用时记录本次回复已写过的记忆，再次以 revise / merge 指向其中任何一条的回复按不合规则处理（§3.1）：
纠正说明要求模型用一个操作写出全部相关事实，其余条目以 noop 指向该记忆。这条规则只在违反时告知模型，
不写入流程指令（§6.3）。noop 不改写目标，不受此限制。

### 3.4 复核（第 3 步）

第 2 步里，一条 create 只和它的检索词召回的记忆比过。第 2 步结束后，Core 用每条 create 的正文再召回一次
（同样取前 5 条），找出第 2 步没有展示过的记忆。都没有则不调用；有则在同一对话里追加第 3 步：
列出这些 create（标签 C1、C2…）和各自的未展示记忆，模型对每条 create 重新给出操作
（create 表示保留，revise / merge 与目标合并，noop 表示目标已包含该事实）。这一步与逐候选流程的一次比对等价，
直接用 `workset.apply(候选, 未展示记忆, 操作)` 应用。第 3 步的请求会重发第 2 步展示过的已有记忆，
因此发送前对这些记忆和新召回的记忆一起重新检查读写权限。

被多条 create 召回的同一条已有记忆只有一个标签，模型能看出它们指向同一条记忆。§3.3 的"最多写一次"在这一步
同样生效：两条 create 都要并入同一条已有记忆时，由一个操作合并，另一条以 noop 指向该记忆。

复核超出输入预算时会拆成几次请求。前一次请求可能已把两条已有记忆合并进一条 create，
后一次请求里这两条记忆的标签都指向合并结果，这时对其中一个标签的 revise 会持有两个已发布身份，
违反"revise 恰好一个已发布身份"的规则。模型先按 §3.1 在纠正次数内重答；纠正次数用尽后，
这次请求列出的 create 原样保留，等同于对每条都选择 create，其余操作不应用，前面请求的决定不变。
代价是可能发布一条重复记忆，或留下未合并的记忆。第 2 步的 revise 目标只有展示过的已有记忆，
各自只有一个已发布身份，不会触发这条规则。

### 3.5 比对范围

现有流程通过 `_recall_related_items` 分页遍历候选的全部相关记忆，比对是穷举的。单次整理每个检索词只取前若干条
召回结果（5 条，总计 40 条），未进入前列的相关记忆只能由复核补上。这是两种模式在比对范围上的本质差异。
另外，同一次回复里的多条 create 之间不做比对，由模型在生成回复时自行避免重复。

## 4. 提示词

流程指令是 `builtin/artifacts/atomic_memory/one_pass.py` 中的代码常量，用户不能修改，相当于 invariant。
其中两处嵌入现有提示词配置：

| 位置 | 来源 |
| --- | --- |
| "什么值得记" | `atomic_memory.extract` 经 `resolve()` 编译后的指令：内置抽取规则（随 profile 变化）；Scope 自定义时还包含其 guidance 与 demonstrations |
| 第 2、3 步的对账原则 | `atomic_memory.reconcile` 的 Scope 自定义指令原文，追加在流程指令之后；未自定义时不追加 |

- 流程指令保持领域中立，不提编码或对话；领域差异全部来自 profile 与 Scope guidance。
- 抽取规则原本面向"输出候选列表"的回复。流程指令在其后说明：选择、措辞、语言与时间方面的规则照常适用，
  输出格式以各步的说明为准。
- `atomic_memory.reconcile` 的内置指令描述的是逐候选回复（`compared_ids` 等），不嵌入；它的 demonstrations
  同样是逐候选格式，单次整理不使用。
- 两个 key 的自定义 Prompt Artifact 都记入本窗口发布条目的 `artifacts`，与逐候选流程一致。
- 带 demonstrations 的 Scope 尚未评测（§7）。

## 5. 配置、预算与失败处理

### 5.1 配置

`RuntimeConfig` 新增 `atomic_memory_processing_mode: Literal["per_candidate", "one_pass"] = "per_candidate"`，
对应环境变量 `POWERCONTEXT_SERVER_RUNTIME_ATOMIC_MEMORY_PROCESSING_MODE`。Server 配置了 `inference.prefix_extraction_gateway_url` 且未显式指定模式时，解析后的运行时默认值为 `one_pass`；显式 `per_candidate` 或 `one_pass` 均优先。SDK 的 `RuntimeConfig` 默认值不变，完整配置序列化中的具体模式也按显式设置处理。
`AtomicMemoryProcessingConfig.from_runtime()` 读取该值。第 1 步的项数上限（30）、每个检索词展示的记忆数（5）
与展示总数上限（40）是 `one_pass.py` 中的常量。

注入自定义 `AtomicMemoryGenerationPipeline` 的部署需要同时提供 `conversation` 生成器才能开启该模式，
否则处理窗口时报 `InferenceUnavailableError`。

### 5.2 预算

所有估算沿用 `atomic_memory_input_tokens_limit` 与管线的 token estimator。每一步估算的是该次请求实际发送的内容：
流程指令、它所续接的对话全文（此前各步的消息、模型回复和纠正请求，由推理接口随回复一并返回），以及本步的新消息。
第 3 步拆成多次调用时，每次调用都只续接第 2 步，各自单独估算。

- 第 1 步或第 2 步的输入超出预算时，本窗口改用逐候选流程（§2）处理。
  第 2 步不拆成多次调用，召回到的已有记忆也不因预算丢弃：逐候选流程在预算不足时本来就会把每次比对的记忆数
  减半直到一条，把第 2 步拆到最细也是同样的调用方式，却要另外处理跨批次的相似条目。回到逐候选流程不引入新的
  行为，代价是该窗口没有成本收益，第 2 步超出时还多付一次第 1 步调用。
- 已有记忆列表最多 40 条。只有窗口证据本身接近预算上限时第 2 步才会超出，这类窗口的占比尚未统计（§7）。
- 第 3 步超出预算时把待复核的 create 对半拆成多次调用，每次都续接第 2 步的回复。各条 create 的复核只针对
  各自的未展示记忆，互不依赖。单条 create 的复核仍超出时按现有的预算错误处理（触发窗口缩减）。
- 每个窗口输出一条 INFO 级别的 `atomic_memory.one_pass` 运行日志：`outcome` 为 `success` 表示操作由这一次对话得出，
  `fallback` 表示因预算改用了逐候选流程，并带上超出的是哪一步（`fallback_reason`）、该请求的估算输入和生效的上限。
  日志不含 Source、记忆、prompt 或回复内容。

### 5.3 接在智能体会话前缀之后

配置了前缀抽取的网关地址（`prefix_extraction_gateway_url`）时，恰好含一个网关回合且带前缀句柄的窗口不再由 Core
重发 Source 正文，而是把整段对话接在网关保留的前缀（智能体的原始请求和最终回答）之后：

```
第 1 步  [前缀] + 用户消息（流程指令 + Source 记录）              ──▶ {"items":[...]}
第 2 步  [前缀] + 同一条用户消息 + 第 1 步回复 + [已有记忆列表]    ──▶ {"operations":[...]}
第 3 步  [前缀] + …… + 第 2 步回复 + [待复核的 create]            ──▶ {"operations":[...]}
```

- **网关接口。** `POST /gateway/v1/extract` 增加可选字段 `continuation`：指令之后的消息列表，从模型回复开始，
  回复与用户消息交替，以用户消息结束（至多 16 条、共 256 KiB）。网关不保存对话，每一步由 Core 重发。
- **流程指令。** 证据所在位置的那一段换成前缀抽取的说明：上面的会话已经结束，只有最近一个用户回合是证据，
  `BEGIN_POWERCONTEXT_*` 标记内的内容不是证据；其余指令逐字相同。Source 记录只含 `evidence_id` 与元数据。
- **同一套步骤。** 召回、应用到 workset、同一目标检查、复核与预算估算都是 §3 的代码，只是对话通道不同。
  回复不合规则时在同一段对话里纠正，纠正请求同样放进 `continuation`。
- **是否划算。** 按每个窗口都有的前两步估算：接在前缀之后的成本为 `2 × 缓存价 × 前缀输入 +
  (1 + 缓存价) × (指令 + 最终回答的输出)`，普通对话为 `(1 + 缓存价) × (流程指令 + 证据)`；前者不低于后者时不使用前缀。
- **回退。** 句柄过期、网关拒绝、检查被暂扣、估算不划算、回复为空，或回复在纠正次数用尽后仍无效时，这段对话的结果
  全部丢弃，窗口按普通的单次整理对话重新开始，并输出 `atomic_memory.prefixed_extraction` 日志（`operation` 为
  `atomic_memory.one_pass`）。此时尚未发布任何内容。已收到的用量照常上报。
- **预算。** 输入预算的估算不含前缀，与前缀抽取相同。第 2 步超出预算时改用逐候选流程，复核超出预算时按 §5.4 缩减
  窗口，两者都不再尝试普通的单次整理对话，因为它的输入只会更大。
- **模型与数据去向。** 这段对话发往智能体自己的目标模型和账号，不经过 Core 的生成模型，与前缀抽取相同。不同的是，
  第 2、3 步展示的已有记忆正文也随之发往该目标；前缀抽取只发送指令和 Source 记录。
- **指令的位置。** 流程指令是智能体会话之后的一条用户消息，不是系统指令，而这段对话直接决定对已有记忆的 revise 与
  merge。会话中的内容（系统消息、工具输出）若带有针对模型的指示，其位置先于流程指令。Core 对回复的校验不变：只能
  操作展示过的标签、同一条已有记忆至多写入一次、引用只能是本窗口的 Source。

这条通道只有脚本化回复的测试覆盖，没有在真实模型上评测过（§7）。

### 5.4 失败与重试

- 任一步输出无效：本窗口按现有 `InvalidInferenceOutputError` 处理，不发布部分结果。
  复核请求在纠正次数用尽后仍违反 revise 的已发布身份规则时例外，按 §3.4 保留这次请求的 create。
- 推理超时：沿用现有窗口缩减与重试逻辑。
- 并发冲突：沿用 `_retry_window` 的三次重试。整窗重试会重新执行两步对话，与现有流程重新抽取的语义一致。

### 5.5 推理接口

现有 `StructuredGenerator` 的实现把输出 schema 写进指令，不同输出格式的两次调用因此没有相同的前缀。
单次整理使用新增的 `PydanticAIConversationGenerator`：输入是 `ConversationTurn`（指令、新消息、此前的对话、
回复检查函数），回复是纯文本，由检查函数解析并校验，返回 `ConversationReply`（检查结果、可续接的对话及其文本）。
它与现有生成器共用同一套超时、请求次数限制、错误映射和用量上报（`UsageReportingStructuredGenerator`），
在链路中的名称为 `atomic_memory_one_pass`。不新增日志字段，不记录提示词与模型输出内容。

## 6. 评测

### 6.1 方法

两种模式由同一份代码启动的两个 Core 实例处理，只有 `atomic_memory_processing_mode` 不同；
抽取规则均为内置 profile，无 Scope guidance，写入、答题与判分所用的模型在两种模式间相同。

- **编码场景**：三个仓库共 15 个连续编码轮次，重复 5 次；每次从空 Scope 开始按顺序写入。
  由 gpt-5.6-sol（high reasoning）盲评最终存储，依据 61 条参考事实（其中 18 条为验证类，其余 43 条为实质事实），
  标注每条记忆是否有用、过时、错误、重复，以及每条参考事实是否被覆盖。
- **对话场景**：LoCoMo 全部 10 段对话，1540 道问题。按会话顺序写入，以 Core 检索的前 10 条记忆作答，
  答题与判分均使用 gpt-5.6-luna。
- **成本单位**：未缓存输入 token 计 1，缓存输入计 0.1，输出计 8，只统计原子记忆写入路径上的模型调用。

### 6.2 结果

**编码场景**（5 次重复合计，实质事实 43 条 × 5 = 215）

| 模式 | 条目 | 平均字符数 | 有用 | 过时 | 重复 | 信噪比 | 实质缺失 | 成本 | 调用数 | 输入缓存占比 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 现有流程 | 88 | 525 | 59 | 27 | 6 | 67% | 13（6.0%） | 7.24M | 354 | 1% |
| 单次整理 | 90 | 670 | 63 | 27 | 19 | 70% | 13（6.0%） | 2.26M | 183 | 54% |

按"同一次重复、同一条事实"配对：只有现有流程漏掉的 5 条，只有单次整理漏掉的 5 条，覆盖度相同。
成本为现有流程的 31%。条数与过时条目和现有流程相同，重复条目更多（19 对 6）。

**对话场景**（LoCoMo，1540 题）

| 模式 | J | 单跳 | 多跳 | 开放域 | 时间 | 存储条数 | 平均字符数 | 成本 | 调用数 | 输入缓存占比 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 现有流程 | 0.801 | 0.723 | 0.819 | 0.635 | 0.838 | 946 | 311 | 41.90M | 4421 | 1% |
| 单次整理 | 0.826 | 0.713 | 0.850 | 0.615 | 0.879 | 1031 | 335 | 8.27M | 857 | 38% |

逐题配对：只有现有流程答对 80 题，只有单次整理答对 119 题（符号检验 p=0.007）。成本为现有流程的 20%。

**重复运行的波动。** 同一份代码、同一配置完整重跑一次（按事实逐条列出的版本，见 §6.3），两次结果为：
编码条目 270 / 275，重复 40 / 45，信噪比 85% / 80%，实质缺失 4.7% / 4.2%；LoCoMo J 0.796 / 0.786。
小于这个幅度的差异不应解读为差别。LoCoMo 上 0.826 对 0.801 的差距超出这个幅度，但只来自一次运行。

**同一目标检查（§3.3）的触发情况。** 上表的运行不含这项检查。带检查的代码在两个场景上完整运行一次
（约 1050 次模型调用），检查没有触发，结果与上表在波动范围内：编码 86 条、平均 703 字符、信噪比 63%、
实质缺失 4.2%、成本 2.24M；LoCoMo J 0.823（配对 83:117，p=0.019）、1026 条、平均 343 字符、成本 8.30M。
编码场景单次重复的信噪比在同一模式内分布于 44%–95%，5 次重复合计值相差 7 个百分点不构成差别。
模型被拒绝后按纠正说明改写的行为只由预设回复的测试覆盖，没有在真实模型上出现过。

### 6.3 评估过的备选方案

前五项在 Core 实现上评测，区别只在流程指令或复核范围；其余各项在接入 Core 之前的流程原型上评测
（同样的数据集与判分方式，证据以对话形式输入）。

| 方案 | 结果 | 结论 |
| --- | --- | --- |
| 第 1 步按事实逐条列出，第 2 步每个事实一条记忆 | 编码 270 条、平均 282 字符、重复 40、实质缺失 4.7%；LoCoMo 0.796、2192 条、平均 166 字符 | 覆盖度与 J 持平，但记忆过碎：同样取前 10 条，得到的信息量约为现有流程的一半。不采用 |
| 同上，复核时把同一窗口内此前的变更也作为比对对象 | 编码重复 39 条，实质缺失 5.6%，成本增加 16% | 没有减少重复，不采用 |
| 第 1 步按事实逐条列出，第 2 步要求把同一话题的事实写成一条 | 编码 56 条、平均 982 字符、信噪比 52%、实质缺失 6.0% | 合并过度，近半数条目被判为过时，不采用 |
| 第 1 步按事实逐条列出，第 2 步把修订放宽为"对同话题已有记忆的任何补充" | 编码 66 条、平均 911 字符、信噪比 52%、实质缺失 6.5%；LoCoMo 0.829（10 段中 9 段，1 段因回复不合规则而失败）、平均 881 字符 | 对话场景 J 高，但编码场景合并过度，且记忆越写越长，不采用 |
| 把"一次回复对同一条已有记忆最多写一次"写进流程指令的第 2、3 步（Core 检查同时启用） | 编码 88 条、平均 703 字符、信噪比 60%、实质缺失 3.7%；LoCoMo 0.822、877 条、平均 409 字符 | J 与成本不变，但对话场景的记忆少 15%、长 22%，粒度偏向合并。规则改为只在违反时告知模型（§3.3） |
| 第 1 步只输出不超过 8 个主题检索词 | 编码实质缺失 16.3%，LoCoMo 0.739 | 同一主题下的多个事实被合并或遗漏，不采用 |
| 第 1 步不说明"只负责检索" | 同一前缀重复 4 次，有 0–2 次返回空列表；编码实质缺失 25.1% | 空列表导致整轮不写入，必须加说明 |
| 第 2 步展示更多已有记忆，并追加"新状态必须修订旧条目"等规则 | 操作分布几乎不变；LoCoMo 降至 0.782（配对 80:109） | 不采用 |
| 在 CODING profile 中要求不记录单次检查结果 | 过时条目减半，但实质缺失升至 15.3% | 以覆盖度换信噪比，不采用 |

过时条目主要是"某某测试通过、共 N 个"之类的时间点快照，现有流程同样存在（27 条），不在本设计中处理。

## 7. 未解决的问题

1. **重复条目。** 编码场景的重复条目多于现有流程（19 对 6，§6.2）。同一次回复里的多条 create 之间不做比对
   （§3.5），已评估的窗口内比对没有减少重复（§6.3）。
2. **Scope demonstrations。** 带 demonstrations 的 Scope 尚未评测；单次整理不使用 `atomic_memory.reconcile`
   的 demonstrations（§4）。
3. **包含多个 Source 的窗口。** 评测中每个窗口只有一个 Source；多个 Source 的窗口可能触达第 1 步的 30 项上限，
   `evidence_ids` 的选择也只在单 Source 窗口上验证过。
4. **改用逐候选流程的窗口占比。** 评测没有统计这一比例。需要在真实 Source 上用 `atomic_memory.one_pass` 日志（§5.2）
   统计因预算改用逐候选流程的窗口比例；占比高到明显抵消成本收益时，再考虑在切分窗口时为已有记忆列表预留预算。
5. **接在智能体会话前缀之后的对话（§5.3）。** 质量和成本都没有评测过：流程指令从系统指令变成了智能体会话之后的
   一条用户消息，模型还能看到更早的回合，执行对话的也是智能体的模型。评测需要让会话真正经过网关；
   同时要统计真实会话里前缀长度与单回合长度的比例，以确定有多少窗口能通过估算。
6. **其他模型服务的前缀缓存。** 成本数据来自一个支持自动前缀缓存的模型服务。不支持前缀缓存、或需要显式
   标记缓存位置的服务上，成本收益会小于 §6.2。

## 8. 全面替换默认模式的条件

同时满足以下条件后，再讨论把单次整理设为默认：

- 编码场景在重复配对评测中，实质缺失不高于现有流程（配对差异不显著或单次整理更优）；
- LoCoMo 的 J 不低于现有流程；
- 成本优势保持；
- 存储条数与每条记忆的长度和现有流程接近。

以上各项在 §6 的评测中已满足。评测只覆盖一个模型服务、内置抽取规则和单 Source 窗口（§7），
当前默认切换仅适用于已配置网关回连地址、且未显式指定模式的 Server。在这些条件之外重复得到同样结果后，再提出替换 SDK 与其他 Server 场景的默认模式。
