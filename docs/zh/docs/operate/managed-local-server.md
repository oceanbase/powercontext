# 受管本地 Server 安装

独立 Ops 工具负责准备固定的 Server 运行环境，并管理当前用户的服务。Ops 使用自己的解释器和依赖，因此修复缺失的 Server 解释器不需要先启动损坏的环境。Desktop 集成通过这一入口完成安装和修复，不要求已有 HTTP 连接。

## 安装与修复计划

安装与修复使用[本地 Server 运维工具](local-server-ops.md)中的 `preflight`、`apply`、`operation_status`、`cancel` 和 `resume` 协议。调用方先展示完整计划，再取得确认并执行。发起请求时保留 operation ID；中断后先查询已保存的尝试和当前事实，再确认恢复计划。

如果后续停止操作替代了中断的修复，应确认新的修复计划，不再恢复已被替代的旧操作。新计划只有在核验原操作记录、安装与资源身份、精确服务定义以及原生命令已结束后，才能接续原修复保护。它不会重启服务，也不会恢复随后已移除的注册。

随包 Ops 解释器每个进程接收一条 JSON 请求。可信宿主提供受保护的资源目录文件，以及分发包固定的 SHA-256 摘要：

```text
<ops-python> -I -S -B <ops-entry.py> --catalog-file <protected-catalog.json> --catalog-sha256 <trusted-sha256>
```

例如，将下面这一行写入标准输入，预检首次安装：

```json
{"protocol_version":1,"request_id":"inspect-install","action":"preflight","operation":"install","options":{}}
```

响应包含固定资源、程序和配置及数据位置、端点、数据库分类、所需空间与启动影响。按共享 Ops 协议，将完整计划原样交给 `apply`，提供唯一 operation ID，并明确授权该 `plan_id`。预检同版本修复时使用 `"operation":"repair"`。受管目录由宿主选择；`--state-dir` 属于独立的 `--target-file` 操作者绑定模式，不能覆盖受管安装位置。这些命令要求已有合格生产者目录，不会自行发现或生成公共发布资源。

只有可信资源生产者能够指定下载 URL、可执行文件布局、平台、架构、包版本和文件摘要。渲染层不能提供命令、下载 URL 或任意安装路径。资源先下载到暂存目录，按固定目录校验后才能发布；与不可信下载一起提供的摘要不能建立信任。缓存命中同样需要通过完整性检查。

修复保持同一固定资源身份和版本，保留安装身份、已有配置和用户数据。它不升级到 `latest`，不重置认证或模型，也不删除已有数据库。替换资源前先停止自有服务，修复完成后不重启；已停止的服务继续停止。对已核验的当前安装重复执行 install，只返回当前事实，不重启服务、不打开数据库。

受管服务定义明确启用隔离运行模式（`isolated_runtime=true`），目标 Python 使用 `-I -B` 启动，排除 `PYTHONPATH` 和用户 site 的导入，并避免生成字节码改变已校验的资源目录。请使用随包 Ops 或匹配版本的服务工具管理这些定义。无法识别该字段的旧版 CLI 会拒绝该定义，不支持用它管理新注册；未包含该字段的已有定义保持原启动行为。

独立安装不会被自动接管。归属未知、控制记录损坏、原生服务定义不一致或原生命令尚未确认结束时，需要先检查再修改。移除服务注册会保留运行环境、配置和数据库，并不删除数据。

## 新建个人配置

新配置明确设置以下选项：

| 设置 | 新受管安装 |
| --- | --- |
| HTTP 监听 | `127.0.0.1` 和计划确认的端口 |
| 数据库 | 用户数据目录中的 SQLite，使用明确的绝对路径 |
| Dashboard | 启用 |
| Access 模式 | `disabled` |
| 旧式 Bearer 认证 | 禁用，不生成 Token |
| MCP | 与 HTTP 使用相同的本地访问模式 |
| 模型 | 不配置生成、Embedding、重排或决策模型 |

这是本地免 Token 访问模式，不是一套额外的匿名凭据。监听地址保持 loopback。该策略不改变已有连接或远程连接的认证要求，修复也不会覆盖用户已有选择。选择已有认证安装时，继续引用其受保护配置。

默认数据目录按平台的 `powercontext_data_dir()` 规则解析，但忽略继承的 `POWERCONTEXT_HOME`。新配置解析也不继承 `POWERCONTEXT_SERVER_*`、`PYTHONPATH` 和 `PYTHONHOME`，并明确保存选定的数据根和 SQLite 路径。已有安装保留已核验的登记数据目录，程序目录与数据目录分开。

预检通过受保护文件接口读取配置，只返回文件身份及必要的本地摘要。配置正文、Token 和模型凭据不进入计划或操作记录。预检不创建配置文件、数据目录或数据库。

## 数据库兼容边界

数据库检查不构造 Server runtime，不连接 SQLite，不初始化表、不修改 WAL 设置，也不执行迁移。它只观察选定文件及恢复侧文件，并将观察结果绑定到精确目标 Server 版本。Ops 自身的包版本不能证明目标 Server 的数据库兼容性。

只修复程序时，计划绑定已有数据库的文件身份和目标版本，允许准备资源期间正常写入及 WAL checkpoint；替换数据库会使计划过期。这种修复观察不授予启动许可，安装和启动仍使用严格的数据库及恢复侧文件观察。

| 观察结果 | 安装器处理 |
| --- | --- |
| 数据库及 SQLite 恢复侧文件均不存在 | 分类为 `new`，确认后的目标 Server 可以在启动时初始化新库。 |
| 已有 SQLite 文件，包括空文件 | 分类为 `existing_unknown`，不自动启动或重启。 |
| 已有文件的数据库头不受支持 | 分类为 `incompatible`，保留文件并阻止启动。 |
| 孤立侧文件、链接或未核验位置、不可读文件、观察过程中发生变化 | 分类为 `unknown`，保留文件并阻止启动。 |

当前公开维护检查只覆盖部分领域，不能证明完整 Server 的 schema、索引、持久任务格式及全部配置能力可用。Dream 或 processing 检查、Atomic Memory 验证、迁移 bundle 的 `ready` 都不能解除安装器的启动阻断。`pc_schema_revision` 标记也不代表整库可用，安装器不会为新库创建该标记。

已有数据缺少固定目标版本的合格整库检查时，应保持服务停止并保留数据库。同版本程序修复可以完成，而数据库继续标记为 `existing_unknown`；修好程序不授予启动许可。当前没有一条能让所有这类数据库变得兼容的通用维护命令。请参阅[数据库迁移](database-migrations.md)了解实际支持的 bundle 边界，并等待支持该数据库的维护版本后再执行数据转换。不要把反复执行局部迁移当成自动修复。

这也限制了当前的日常操作：首次启动创建数据库后，只要整库兼容性仍为未知，受管入口后续的 `start`、`restart`，以及会实际重启运行中服务的 `config_apply(restart=true)` 都会被拒绝。原本停止的服务在配置修改后仍保持停止，即使传入 `restart=true` 也不会启动。历史启动成功或安装清单不能绕过该检查。检查、停止、不重启的配置修改和同版本程序修复仍可执行。对自有当前安装重复执行 `install` 只返回事实。因此，这一实现尚不具备完整的日常重启流程，仍需补齐合格的整库检查。独立的已备妥 runtime 操作者绑定保留既有契约，也不能用它证明受管数据库兼容。

## 启动与连接交接

资源完整性、配置有效性、服务注册、进程存活和 readiness 是不同事实。获得首次启动授权后，共享服务控制器执行有界 readiness 验证；本次新启动的自有目标失败时，会恢复保护并确认停止。已完成安装的结果是历史事实，普通状态查询不重新执行 readiness。取消只在支持的安全边界生效，并不承诺回滚。

如果首次注册在创建服务前失败，释放冲突端口或解决报告的问题后，确认新的 install 计划并恢复原操作，安装身份和自有配置会保留。派发检查点本身不能证明注册已经存在。匹配版本的 CLI 和 Ops 在修改原生注册前保存受保护的移除身份，旧安装操作不能撤销之后的明确移除，即使当时尚未创建注册。不含该身份的旧记录仍可读取，但缺少注册证据的旧派发检查点需要先检查，不会自动重放。

取消后的安装可复用已核验暂存资源。如果普通暂存文件损坏，resume 或新批准的 install 操作会核对已记录的目录归属，只清理对应暂存树，再次准备同一固定资源。目录被替换、包含链接或归属不安全时，拒绝操作并保留现场。

安装器返回实际端点和安装、资源身份，这些信息不是 Server 部署或 Principal 身份。连接负责方仍需根据公开身份和兼容契约核验真实端点，才能激活连接并取得默认 Scope。安装不会自造 Scope ID、任意选择一个 Scope，也不证明 Memory 操作已成功。

## 发布与平台验收

实现要求生产者提供固定资源。[候选生产器](../../development/managed-resource-production.md)为 Windows x86_64 和 macOS arm64/x86_64
原生构建固定的 Server/Ops 资源，并通过真实消费者回读；其 catalog 仍未资格验收。正式平台资源目录及合格产物归
[#2112](https://github.com/oceanbase/powercontext/issues/2112) 负责；实现不提供公共生产下载 URL，也不会根据版本号猜测地址。
开发 fixture 和本地构建包验证的是实现行为，不能证明生产分发可信。

Windows 预检会根据实际最终目录和固定暂存路径预算检查资源布局，获取资源时还会在下载前核对本次暂存目录。普通路径必须满足 Windows 文件和目录长度限制，不支持的布局返回 `resource_path_unsupported`。Ops 不修改系统长路径设置，也不假定 Task Scheduler 支持扩展路径形式的可执行文件名。生产者需提供适合目标用户目录的合格布局；完整开发包在较短测试目录中启动成功，不能证明默认安装布局可用。

发布验收需使用实际下载产物，在未预装 Python、uv、Git 或编译工具的干净普通用户 Windows 11 x64、macOS arm64 和 macOS x86_64 环境执行。分别验证签名与 macOS notarization、独立 Ops 启动、真实 Task Scheduler 或 LaunchAgent 行为、登录与重启，以及修复和移除后的配置与数据保留。Fake 服务适配器和仓库 runtime 的 SQLite 测试不能替代这些平台证据。
