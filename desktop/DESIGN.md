# Design Specification

This file is the sole design specification at the repository root. It defines the visual rules, interaction rules, constraints, and design tokens for PowerContext Desktop. Use it for product design, visual QA, component implementation, and AI-generated interfaces. CSS, Tailwind, shadcn components, and high-fidelity designs derive from this specification. If they conflict, this file takes precedence.

The rules apply across the product by default. Sections help readers find related rules. Every page and component must follow all applicable rules unless a rule explicitly states an exception. Apply the same visual and interaction rules across page, module, and feature boundaries.

Sections 1–5 define the brand, visual and interaction rules, and tokens. Section 6 covers reusable page layouts. Sections 7 and 8 define component and icon contracts. Section 9 covers data visualization, Section 10 covers first-run guidance, and Section 11 covers adaptation to window sizes and user preferences. Section 12 defines how the specification translates into code. Product and feature specifications own individual fields, UI copy, data, workflows, permissions, mock states, and development preview behavior.

---

## 1. Brand and Visual Language

**Positioning. A calm, dependable workspace for AI memory.** PowerContext Desktop should feel like a mature productivity app that stays clear and comfortable over long sessions. Keep the interface restrained. Avoid developer-console styling and marketing-site effects.

The interface should answer three questions first. Which service is in use? Which space is open? Can the current task continue? Reveal technical details when they help users make a decision, configure the product, or recover from a problem.

### 1.1 Brand Pillars

| Pillar | Visual expression | Intent |
| --- | --- | --- |
| Codex neutrals | White, near-black, and neutral grays make up most of the interface | Give the interface a professional, trustworthy feel and keep attention on the data and the task |
| Clear context | Keep the service, its status, and the current space visible in the global context bar | Make it clear where a write will go |
| Lightweight structure | Use whitespace, `1px` dividers, and a small number of surface levels | Organize content without a wall of cards |
| Compact memory browsing | Use density comparable to the Stripe Dashboard by default. Keep the memory list denser | Make frequent scanning and long work sessions comfortable |
| Native desktop feel | Use system fonts, window controls, stable navigation, and restrained motion | Make the app feel familiar, responsive, and dependable |

### 1.2 Tone and Boundaries

**Aim for** a calm, dependable, clear, scannable, flat interface that puts real data first.

**Avoid** developer tools, infrastructure consoles, neon AI styling, glass effects, decorative gradients, and sparse marketing layouts.

**Signature elements** include the neutral sidebar, near-black primary actions, thin dividers, consistent context bar, and compact memory list. One or two per view are enough. Avoid stacking them all into a single view.

### 1.3 Design Principles

| Dimension | Standard |
| --- | --- |
| Information density | 6/10 overall. Use moderate density on Home and 8/10 in the memory list |
| Layout variation | 5/10. Rearrange content within the stable app shell to suit the task |
| Motion | 3/10. Use it for feedback and to show spatial relationships |
| Visual refinement | 6/10. Rely on typography, spacing, and boundaries. Keep decoration out of the way |

**Required.** Always make the current service, service status, and space clear. Prioritize real state. Prefer lists and description lists to grids of cards.

**Prohibited.** Blue as the default primary action color, fabricated agent information or statistics, cream backgrounds, grids of heavily rounded cards, and oversized marketing headlines.

## 2. Visual Rules

### 2.1 Surface Hierarchy

`Canvas → Content surface → Subtle surface → Selected surface`

| Layer | Token | Use |
| --- | --- | --- |
| Canvas | `--pc-color-canvas` | Main content background and top context bar |
| Content surface | `--pc-color-surface` | Inputs, menus, dialogs, and standalone containers |
| Subtle surface | `--pc-color-surface-subtle` | Sidebar and lightweight sections |
| Muted surface | `--pc-color-surface-muted` | Disabled states, skeletons, and tracks |
| Selected surface | `--pc-color-surface-selected` | Current navigation item, selected rows, and subtle hover states |

Use at most three contrasting solid surface levels in a single viewport. Establish static hierarchy with backgrounds, whitespace, and borders. Avoid stacking shadows.

### 2.2 Border and Focus States

| State | Treatment | Token |
| --- | --- | --- |
| Default | `1px` quiet or transparent border | `--pc-color-border` |
| Hover | Increase background or border contrast. Keep the element in place | `--pc-color-surface-selected` / `--pc-color-border-strong` |
| Focus / open | Use an action-colored border for fields and an outer focus ring for other controls | `--pc-color-action` / `--pc-borders-focus-*` |
| Selected | Selected surface and `500` font weight | `--pc-color-surface-selected` |
| Error | Destructive border, icon, and recovery instructions | `--pc-color-destructive` |

Focus takes precedence over hover. Pair color with text, an icon, or position to communicate state.

### 2.3 Shape and Elevation

- Use `rounded-md` for standard controls, `rounded-sm` for compact controls, `rounded-lg` for containers, and `rounded-xs` for small data cells. The frontmatter defines the values.
- Keep pages, sidebars, top bars, and ordinary containers shadow-free. Reserve the elevation tokens for dropdowns, popovers, dialogs, toasts, and tooltips.
- Use the near-black action surface for primary actions. Avoid brand blue, gradients, glows, and glass effects.
- Use solid surfaces, whitespace, `1px` boundaries, and typography to establish static hierarchy. Avoid translucent blur.
- Use containers only for distinct groups, action boundaries, or independently scrollable regions. Do not nest cards.
- Do not use decorative gradients, glass effects, colored glows, or textures that convey no information.

### 2.4 Information Density

- Space page sections `24–32px` apart by default. Space related controls `8–12px` apart.
- Use a `40px` row height and `8px 12px` padding in the memory list. Limit text previews to two lines.
- Use `controls.height-field` for text-style form fields, including Input, Select, and Textarea. Checkbox, Switch, and Radio follow their own component dimensions. Space field groups `space-5` to `space-6` apart.
- Preserve the size and visibility of critical status indicators, recovery actions, and touch targets in dense layouts.

## 3. Interaction Rules

### 3.1 Feedback Levels

| Level | Use | Treatment |
| --- | --- | --- |
| L0 Static | Read-only content | Keep it still. Truncate long content and offer access to the full text |
| L1 Microfeedback | Hover, toggles, or period changes | Change color or border over `150–180ms` |
| L2 Spatial change | Detail panes, sheets, and collapsible sections | Animate opacity and transform over `180–220ms` |
| L3 Overlay | Menus, popovers, and dialogs | Use a portal and manage focus. Use a backdrop or shadow as appropriate |
| L4 Confirmation | Irreversible actions such as deleting or disconnecting | State the outcome and focus the safe action by default |

### 3.2 Focus and Overlays

- Give every keyboard-operable control a visible focus indicator and a complete accessible name.
- Trap focus inside an open dialog and return it to the trigger when the dialog closes.
- Use a Radix Portal for overlays that may extend beyond a scroll container.
- Allow one top-level overlay at a time. Escape closes the topmost overlay.

### 3.3 Motion Budget

- Animate only `opacity`, `transform`, color, and strokes. Do not animate width, height, margins, or other properties that shift the layout.
- Use `motion-press` for press feedback, `motion-fast / standard` for hover and focus, and `motion-floating` for menus, dialogs, and notifications.
- Keep page content still on entry by default. Reserve short fades with small translations for overlays, notifications, and locally expanding regions.
- Do not use bounce without a triggering gesture, overshoot, decorative loops, or page-wide animation sequences. Reserve continuous animation for explicit loading states and pair it with text.
- With `prefers-reduced-motion: reduce`, remove unnecessary movement and entrance animation. Use a static indicator or gentler motion for essential loading feedback.

### 3.4 Forms and Submission

- Keep labels visible and use placeholders only as supplementary text. Place errors below their fields.
- Preserve user input on error and state what the user can do to recover.
- Use `disabled` and its corresponding visual treatment for unavailable controls. Keep `readOnly` controls focusable and allow users to select and copy their values. Muted surfaces, secondary text, and quiet borders can distinguish read-only fields. Reserve disabled attributes, semantics, and component states for unavailable controls.
- Bind submissions to the service and space that will receive the write. If the context changes, tell the user explicitly. Never silently redirect a write.

### 3.5 Button Hierarchy

- Use only the `default` and `sm` heights for action buttons. The `sm` size maps to `controls.height-compact`. Primary, secondary, destructive, and icon buttons share these heights, which the frontmatter defines.
- Use the default height for page-level primary actions and standard form actions. Use the compact height in list rows, dialog action bars, and constrained areas.
- Use `typography.action` for every action button. Use the action fill for primary emphasis. Keep the standard font weight and avoid page-specific CSS that resizes buttons or changes their weight.
- Use `lg` only for extra horizontal padding at the default height. Text-only links are inline actions and introduce no separate button height.
- Use the inline `text` variant of `Button` to expand or collapse content. Use secondary text by default and darken it on hover and press. Keep the keyboard focus ring and omit fill, underline, and horizontal padding. Use `space-4` padding on conversation excerpt cards and `space-2` between the title, body, and expand action.
- Prefer one height within a group. Express priority through fill, border, and text treatment. Keep the shared size scale.

## 4. Design Tokens

The frontmatter is the sole source for implementation tokens. Run `pnpm design:tokens` to generate `desktop/ui/src/generated/design-tokens.css`. Always regenerate that file instead of editing it by hand. The generated tokens supply design values. Keep component structure, variants, and interaction states in the project's shadcn components, where product code can use them directly. Avoid global selectors that override those contracts.

## 6. Page Layouts

This section defines structures that can be reused across pages. Use Section 4.4 for spacing and sizing, Section 7 for component layouts, and Section 11 for breakpoint behavior. Product and feature specifications define the modules, fields, copy, and workflows.

**App shell.** Fill the window vertically with a fixed sidebar, top context bar, and flexible content area. The sidebar spans the full height. Keep the context bar separate from the page body, and scroll the body within its content area. Keep the shell free of horizontal overflow.

**Standard content page.** Use for overviews, data views, and multi-column workspaces. Arrange the page as heading, optional toolbar, then content. Use `layout-content-max-width` and align content to the left by default. Keep the outer content shell within `layout-shell-max-width`.

**Narrow content page.** Use for settings, single-column configuration, and sustained reading. Center the content horizontally within `layout-content-narrow-max-width`. Stack sections vertically with more space between sections than between items in a section.

**Centered decision page.** Use for first run, full-page empty states, and a small set of clear choices. Center the decision area within `layout-onboarding-max-width` and keep the options within `layout-onboarding-choices-max-width`. When space is limited, stack the options in reading order.

**List-detail page.** Let the main pane fill the remaining space. Use `layout-details-width-default` for the detail pane, with `layout-details-width-min` as the minimum. The main and detail panes scroll independently. Keep the detail heading and tools visible while its body scrolls. Use a standalone detail view in compact windows to avoid squeezing both panes into an unusable width.

**Grouped content page.** Related lists, description lists, and settings items share one continuous surface. Use whitespace, headings, and `1px` dividers to establish hierarchy. Omit extra spacing below the last item. Keep individual items and metrics within their group instead of making each a card.

### 6.1 Layout Behavior

Follow the motion budget in Section 3. Limit layout changes to the affected regions, keep the rest of the page stable, and avoid size animations.

| Region | Change | Rule |
| --- | --- | --- |
| Page body | Scroll | Scroll only the content area. Keep the sidebar and context bar stable |
| Context bar | Narrow or short window | Move into normal document flow when needed to give menus enough room |
| List-detail layout | Open details | Adjust only the main and detail panes. Keep other page regions in place |
| List-detail layout | Expand details | Hide the main pane and reuse the existing detail content. Avoid duplicating the structure |
| List-detail layout | Compact window | Switch to one column or a standalone detail view |
| Sidebar | Narrow window | Switch the shell to one column and reveal a separate navigation area from the mobile navigation control |
| Two-column content | Limited space | Stack the columns in reading order |
| Settings row | Limited space | Keep the description first. Move the control to the next line with its full hit area |

Keep unaffected areas stable during layout changes. Do not use full-screen backdrops for ordinary split-pane changes. Do not use unexplained fixed heights, empty spacer elements, or page-specific negative margins to create structure.

## 7. UI Patterns

Use these patterns to choose the right interface for a given situation. They connect the visual rules in Section 2, the interaction rules in Section 3, and the tokens in Section 4. See Section 12.2 for component mappings and where migration is needed. Product and feature specifications define the fields, UI copy, data, and workflows.

| Pattern | Visual treatment (§2) | Interaction (§3) | Key tokens |
| --- | --- | --- | --- |
| Primary button | Action fill with inverse text | L1. Prevent duplicate submission | `color-action`, `height-default / compact` |
| Secondary button | Surface with a quiet border | L1. Strengthen the border on hover | `color-surface`, `color-border-strong` |
| Icon button | Transparent or subtle surface | L1. Provide an accessible name or tooltip | `icon-*`, `target-min / touch` |
| Navigation item | Selected surface for the current item | L1. Indicate the current page | `height-nav`, `color-surface-selected` |
| Input and selection | Field border states | Show form errors where they occur | `height-field`, `rounded-md`, `color-border` |
| Menu | Surface with a floating shadow | L3. Allow only one top-level overlay | `shadows-floating`, `z-index-dropdown` |
| List row | Continuous surface with dividers | L1. Subtle background on hover | `color-border`, `color-surface-hover` |
| Panel | Surface with a quiet border and no static shadow | L0/L1. Use for a distinct purpose | `rounded-lg`, `color-border` |
| Accordion | Continuous grouped surface | L1. Keep unrelated regions stable on expansion | `color-border`, `motion-standard` |
| Badge | Subtle semantic surface and text label | L0. Pair color with another signal | Semantic color, `rounded-full` |
| Dialog | Backdrop and dialog surface | L3. Use L4 for destructive confirmations | `color-overlay`, `shadows-dialog` |
| Feedback | State-specific icon, title, and description | L0/L1/L4. Prefer feedback in place | Semantic color, `typography-action` |
| Loading | Muted placeholder or status text | L0. Preserve the final layout | `color-surface-muted`, `motion-*` |
| Empty state | Icon, title, description, and optional action | L0. Preserve the region's layout | Typography, spacing |

Use panels and cards only for distinct groups, action boundaries, or independently scrollable regions. Do not fill a page with floating cards, nest cards, or put every metric in its own card.

### 7.1 Menus

| Type | Use | Rule |
| --- | --- | --- |
| DropdownMenu | Run an action on the current item | Group actions when helpful and clearly mark destructive actions. Keep form values out of action menus |
| Select | Choose one form value from a finite set | Show the current value and mark the selected option with a check. Keep executable actions out of the list |
| Popover | Show supporting information, simple filters, or brief context | Keep it lightweight. Use a page or dialog for complex tasks |

All three use a surface, quiet border, `rounded-md`, and floating shadow. Hover and keyboard highlight affect the background only. Render overlays in a portal, support keyboard navigation and Escape, and restore focus on close. Use a separator to group related actions. Keep menus shallow enough to avoid turning them into small pages.

### 7.2 Feedback

| Situation | Treatment | Rule |
| --- | --- | --- |
| Page or region status | Inline feedback block | Keep it next to the affected content. It can contain a title, description, and recovery action |
| Field error | Field border and error below | Keep user input and clear the stale error as soon as it is resolved |
| Non-blocking completion | Notification at the edge of the viewport | It can dismiss automatically. Keep the current task uninterrupted |
| Empty state | Icon, title, description, and optional action | Keep page-level and local empty states within their own layout regions |
| Warning or error | Semantic surface, icon, and explicit copy | Use persistent feedback when the user needs to act |

Use `action-emphasis` for feedback titles and `action` for the body. Align the icon with the title. Pair the color with another status signal. Use `aria-live="polite"` or `role="status"` for routine updates and `role="alert"` for errors that require immediate announcement.

Use `spacing-3` on all sides of a compact Alert and `spacing-4` for a standard page-level Alert. Use `spacing-1` between the title and description and `spacing-2` between the icon and text. Apply the status color to the title and icon, and use secondary text color for the description. Keep all four borders the same width and avoid a thick accent border on one side.

### 7.3 Loading

Loading is L0. Keep it unobtrusive and stable, and leave focus where it is. Match placeholder dimensions to the final content and block only the region being updated.

| Situation | Treatment | Rule |
| --- | --- | --- |
| Initial page load | Preserve the app shell and page structure | Avoid a full-screen backdrop or centered spinner |
| Lists, statistics, and details | Matching placeholders or regional status text | Clear stale data from a previous context and keep the layout stable when loading finishes |
| Buttons and inline actions | Loading text or a busy state that preserves the button width | Prevent duplicate actions and leave unrelated controls available |
| Background update | Lightweight status near the trigger | Keep the region uncovered when its content remains usable |
| Long task with known progress | Progress bar and progress text | State the current stage or completion percentage |

Distinguish loading, empty, error, and unavailable states. Label unknown results explicitly. Use `0` only for a known zero. Match skeletons to the final structure and use `surface-muted`. Remove pulsing under reduced motion. Include text for loading states so animation is never the only signal.

### 7.4 Dialogs

| Type | Use | Rule |
| --- | --- | --- |
| Standard dialog | Short, focused task | Keep the title, content, and actions in a stable structure. Provide cancel and close controls |
| Confirmation dialog | Irreversible or high-risk action | Use L4. Explain the impact and focus the safe action by default |
| Long-content dialog | Long form, list, or preview | Keep the title and actions visible and scroll the content independently. Use a page if needed |

Render the dialog through a portal with a backdrop, dialog surface, and dialog shadow. Trap focus while it is open. Escape closes the topmost dialog and focus returns to its trigger. Center the title across the entire header. Reserve space on the left equal to the width of the close button on the right to keep the title centered. Use `layout-dialog-max-width` for form dialogs and keep them within the safe area of the viewport. See Sections 4.2 and 4.4 for title, content, and action sizing, and Section 11 for viewport behavior. On failure, keep the dialog open, retain the user's input, and show feedback in place.

### 7.5 Forms

| Pattern | Use | Rule |
| --- | --- | --- |
| Input | Single-line text, addresses, numbers, or credentials | Keep the label visible. Use placeholder text only for examples |
| Select | Choose one value from a finite set | Reserve it for values. Prefer read-only text for a value the user cannot change |
| Textarea | Multiline content, descriptions, or a copyable preview | Set a practical minimum height and allow long content to scroll inside |
| Checkbox | Individual or bulk selection | Allow multiple selections and associate the clickable label with the control |
| Switch | Binary setting that takes effect immediately | Use a label that describes the setting. Keep submission confirmation separate |
| Read-only | View, select, and copy a value that cannot be edited | Keep the field focusable and reserve disabled semantics for unavailable controls |

Place the label first, then the field, then help or error text. Input, Select, and Textarea share the same field styling and use a `1px` action-colored focus border. Keep errors next to the field and preserve the input. Use `disabled` for unavailable controls and `readOnly` for readable, non-editable fields. Block only the action being submitted and show request failures within the form. See Section 4.4 for sizing and spacing and Section 6.1 for responsive layout.

## 9. Charts and Data Visualization

The activity calendar on Home is the primary visualization. Before adding a chart, show that it communicates the data more clearly than a number, list, or description list.

- Use neutral tokens for coordinates, gridlines, and axis labels. Use semantic status colors for positive, warning, and negative values.
- Encode activity using only `--pc-color-activity-1` through `activity-4`.
- Use light gray for inactive heatmap cells and four shades of blue, from light to dark, for active cells. Use Info blue (`--pc-color-info`) for the **In use** status dot in the memory overview. Reserve Success green for success states.
- Use a surface, quiet border, and floating shadow for tooltips. Render them through a portal to avoid clipping.
- Keep container sizes stable and highlight only the hovered item. Supplement color with labels, values, or a screen reader summary.
- Do not use decorative gradients, 3D charts, numbers without units, or fabricated trends.

## 10. First Run and Guidance

- On first launch, ask **Do you already have a service?** Offer **Connect an existing service** and **Install on this computer**. Let the user choose where the service runs.
- After the user chooses local installation, check for an existing PowerContext environment and guide them through installation, configuration, and startup.
- When the user chooses to connect an existing service, support both local and remote services. Guide them through entering connection details and the access token.
- Require an agent connection to complete basic setup. Model configuration and launch at startup can be completed later.
- At each step, explain what the checks found, what to do next, and how to tell when the step is complete. Use language readers can understand without knowing the protocols or internal modules.
- Let users revisit completed steps. On failure, keep their input and provide a way to retry or open diagnostics.
- Keep guidance within the app shell. Avoid separate, marketing-style landing pages.

## 11. Responsive Layout and Window Behavior

- Support a minimum window size of `400 × 400px` and keep core actions accessible.
- Use `layout-breakpoint-wide` to tighten wide grids. Use `layout-breakpoint-compact` to switch two-column content and list-detail layouts to one column.
- Use `layout-breakpoint-mobile` to reflow settings rows, forms, and content toolbars. Use `layout-breakpoint-shell-mobile` to switch the app shell to one column and collapse the sidebar. Keep breakpoints with different roles separate even when their values are close.
- Below `layout-breakpoint-short-height`, the context bar can move into normal document flow. Position menus within the viewport and cap their height.
- Cap overlays at `calc(100vw - 32px)`. Wrap long addresses or allow them to scroll horizontally to keep the layout intact.
- Reflow the layout while preserving the size of body text, fields, and critical hit areas. Stack two-column content in reading order and use a standalone detail view.
- Use at least `controls.target-touch` for touch targets. Match keyboard focus order to visual order.
- Verify both themes, Chinese and English, 200% zoom, and reduced motion.
- Support `prefers-reduced-transparency` by removing blur from floating surfaces. Support `prefers-contrast: more` by strengthening container borders and focus rings.

## 12. Implementation Contracts and Anti-Patterns

### 12.1 Implementation Contract

1. Update the frontmatter, run `pnpm design:tokens`, and then update the project's shadcn components. Always regenerate generated files instead of editing them by hand.
2. Follow the dependency chain `DESIGN.md → design-tokens.css → components/ui → product pages`. Tokens supply the design values. The shadcn/Radix source in `components/ui` defines structure, variants, state, interaction, and accessibility. Product pages use those components directly.
3. Use the project's shadcn source in `components/ui`. Avoid purely visual wrappers with no product meaning, such as `AppButton`, `PowerContextInput`, or `CustomDialog`. Compose shared components such as `PageActionButton` only for stable, recurring product patterns.
4. Define focus, disabled and read-only states, dimensions, variants, corner radii, and motion in `components/ui`. Keep `style.css` for page layout, product content arrangement, and responsive behavior. Avoid global or page-specific selectors that override base component rules.
5. Product code uses only generated tokens, the shadcn semantic variables mapped from them, and the project components in `components/ui`. Reuse existing variants and avoid re-creating them with native controls and page classes such as `.primary`.
6. Apply the entire specification across the product. When choosing UI patterns for a new page, follow the brand, visual, interaction, component, responsive, and implementation rules together.
7. Treat raw colors, arbitrary radii or z-index values, page-specific font stacks, and animation without a reduced-motion treatment as design defects.
8. At minimum, design QA must check context accuracy, data authenticity, keyboard access, contrast, overflow, and empty, zero, error, and loading states.

### 12.3 Anti-Patterns

- Treating CSS, component source, or design mockups as the source of the specification.
- Default blue as the primary color, cream or sand backgrounds, neon, gradient text, glass effects, or decorative glows.
- Thick colored borders on one side, layouts dominated by oversized numbers, grids of same-size cards, or nested cards.
- Leading with protocol names, status codes, opaque IDs, or raw diagnostics.
- Using color as the only status signal or assigning the same color a different meaning.
- Bypassing shadcn/Radix to implement focus traps, keyboard menus, selects, or dialogs.
- Fabricating agents, statistics, activity times, trends, or service capabilities when backend data is unavailable.
- Animating properties that change layout, opening multiple top-level overlays, or showing errors only in a transient toast.
