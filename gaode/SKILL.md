# 周边探索（nearby-explorer）

回答“附近有什么值得去的地方”这一类问题。核心原则只有一条：**地点、地址、距离、耗时都必须来自高德地图 MCP 工具的真实返回，一个字都不能自己编**。查不到就说查不到。

一次任务的核心流程是五步：**定位起点 → 周边搜索 → 测真实步行路线 → 筛选排序 → 按格式输出**。

---

## 1. 可用工具

本 Skill 只依赖平台已挂载的高德地图 MCP Server（`https://mcp.amap.com/mcp`）的以下工具。**不要**假设存在其他工具，也不要用自己的常识补充地点数据。

| 工具名 | 作用 | 关键参数 | 返回里可用字段 | 本 Skill 中的用途 |
|---|---|---|---|---|
| `maps_geo` | 地址/地标 → 经纬度 | `address`、`city` | **`return` 是数组**，取 `return[0]` 里的 `location`（“经度,纬度”）、`level`、`city`、`district`、`adcode` | 把起点文字解析成坐标 |
| `maps_regeocode` | 经纬度 → 行政区 | `location` | `provice`、`city`、`district` | 起点只给了坐标时，判断属于哪个城市 |
| `maps_text_search` | 关键词搜索 POI | `keywords`、`city`、`types` | `id`、`name`、`address`、`typecode` | 找特定店名/品牌/地标 |
| `maps_around_search` | 以某点为圆心的周边搜索 | `location`、`radius`、`keywords` | `id`、`name`、`address`、`typecode` | **主力工具**：以起点为中心找附近同类地点 |
| `maps_search_detail` | 按 POI ID 查详情 | `id` | `location`、`address`、`type`、`business_area`，以及 `biz_ext` 里的营业时间/评分（可能没有） | 把候选 POI 换成**精确坐标**，再取营业信息 |
| `maps_direction_walking` | 步行路径规划 | `origin`、`destination`（均为“经度,纬度”） | `route.paths` 数组 → `paths[0].distance`（米）、`paths[0].duration`（秒）、`paths[0].steps[]` | **唯一**的步行距离/耗时来源 |
| `maps_distance` | 两点距离测量 | `origins`、`destination`、`type`（`3` 为步行） | `results[].distance`（米）、`results[].duration`（秒） | **仅**在步行规划失败时作降级参考，不能当正常来源 |

（另有 `maps_weather`、`maps_direction_driving`、`maps_direction_transit_integrated`、`maps_bicycling`、`maps_ip_location`，本 Skill 流程不需要，**不要调用**。用户明确问“开车/骑车/坐地铁多久”时，超出本 Skill 范围，直接说明即可。）

### 工具调用硬规则

1. **坐标格式**：所有经纬度一律写成 `经度,纬度`，如 `116.397128,39.916527`。经纬度不可颠倒，颠倒后响应会直接报错或算错距离。
2. **`maps_text_search` 和 `maps_around_search` 都不返回坐标**：只能用返回的 `id` 调 `maps_search_detail` 拿 `location`。
3. **`maps_geo` 的坐标在 `return[0].location`**，不是响应顶层的 `location`。`return` 为空数组才算定位失败。
4. **`maps_around_search` 的 `radius` 是米**，取字符串，如 `"2000"`。半径只影响召回，不影响结论——**是否“步行可达”只以 `maps_direction_walking` 为准**。
5. **`maps_direction_walking` 的 `distance` 单位是米、`duration` 单位是秒**，展示时按 `duration / 60` 向上取整成分钟。
6. **`paths` 可能为空数组**：即便调用成功（没有 `isError`），`paths` 为空也等于该点没有步行路线，按第 3 步失败分支处理；**不能**自行用直线距离或步行速度估算，唯一允许的降级是按第 3 步用 `maps_distance(type="3")` 并明确标注。
7. **`maps_distance(type="3")` 的 `duration` 不是真实步行耗时**，只能作降级参考，必须标注。
8. **一次只调用一个工具，看到返回再决定下一步**，没拿到坐标前不要发起路线规划。
9. 工具返回 `isError: true` 时，文本里通常是 `xxx failed: <info/infocode>`，把它记入“查询异常”，按第 6 节降级，**不要**用记忆里的数据顶替。

## 2. 工作流程

### 第 0 步：解析任务输入

从用户输入里提取下面六个槽位（统称“需求槽位”）：

| 槽位 | 示例 | 缺失时 |
|---|---|---|
| 城市 | “北京”“上海” | 由起点解析结果补全（`maps_geo` 返回的 `city` / `maps_regeocode` 返回的 `city`） |
| 起点 | “杭州东站地铁站”“中关村地铁站 A 口” | 无起点则无法算距离，按第 6 节“起点定位失败”处理 |
| 类型 | 咖啡馆、餐厅、公园、书店…… | 无法确定时按“周边综合探索”处理，并在回答中说明假设 |
| 时间上限 | “15 分钟内”“10 分钟能走到” | 默认 **15 分钟** |
| 数量 | “推荐 3 家” | 默认 **3 个**，最多推荐 **5 个** |
| 偏好排序 | “优先近一点的”“环境好的” | 默认按步行耗时从近到远 |

**默认值必须在 3.1 开头句里显式写出来**（如“按默认 15 分钟单程步行、默认 3 个”），没写即视为输出不合格。

**时间上限只做一种解释**：单程步行耗时（分钟），即从起点出发、去程要走多少分钟。若用户表达的是“往返总共 X 分钟”，单程上限取 `floor(X / 2)`（25 分钟往返 → 12 分钟单程），并在开头句写明这个换算。**不要**自行解释成“加上停留/坐在店里的时间”。

**需求互相矛盾时**（例如“步行 5 分钟内 + 必须带儿童区 + 还想要 4.8 分以上”）：先按不改偏好的规则检索；若确实没有同时满足的候选，再按第 6 节**显式建议放宽哪个条件**，**不要**擅自放宽后当成满足条件。

### 第 1 步：把起点转成坐标（定位起点）

按以下顺序尝试，第一个成功即止：

1. 起点本身已是“经度,纬度” → 直接用；再用 `maps_regeocode` 确认城市。
2. 起点是地铁站/地标/地址 → `maps_geo(address=起点, city=城市)` 查坐标。**结果必须校验**：
   - 取 `return[0].location`。若 `return` 为空数组，或 `return[0].location` 为空、`level` 明显与用户描述不符（用户说地铁站，返回的却是省份/城市级）→ 视为**定位失败**，转到第 3 条。
   - 坐标合格 → 记录 `return[0].location`、`city`、`district`、`level`。
3. 第 2 条失败时，用 `maps_text_search`（`keywords` = 起点全称，`city` = 城市），再用 `maps_search_detail` 取 `location`。
4. 仍然失败 → 进入第 6 节“起点定位失败”，并说明“未能把起点解析成坐标，无法计算步行路线”。

记录：`起点名 = 查询命中名`、`起点坐标 = location`、`起点行政区 = city/district`。

> 起点名称以**查询命中名**为准写进回答（例如用户说“地铁站”，命中名是“XX地铁站 A 口”），不要把用户的原话当地址写。

### 第 2 步：搜索候选地点（周边搜索）

1. 用 `maps_around_search`，`location` = 起点坐标，`radius` 取 **`2000`**（米），`keywords` = 类型关键词。若时间上限 ≤ 5 分钟，可把 `radius` 降到 `1000` 减少无关召回（只是少召回，**不改变**达标判定）。
   - 半径只决定召回范围。**不要**用半径或任何经验值预先判断“是否可达”——是否达标一律等 `maps_direction_walking` 的真实结果。
2. 若候选少于用户要求的数量，再补一次检索（去重口径见本步第 4 条，去重后不足即补搜）：
   - 换半径到 `3000`；或
   - 换 `keywords` 的近义词再搜一次（如“咖啡” ↔ “咖啡馆” ↔ “咖啡厅”；“餐厅” ↔ “饭店”；“公园” ↔ “绿道”）。
   - 最多补搜 2 次。仍不足则按第 6 节“达标数量不足”与“周边搜索 0 结果”处理。
3. 对**每个候选 POI**，用 `maps_search_detail`（`id` = 上一步的 `id`）取 `location`。**没有坐标的候选不能进入路线测量环节。**
   - 顺带记录 `type`（判断是否真的属于用户要的类型，例如“咖啡馆”而不是“茶饮/便利店”）、`address`，以及 `biz_ext` 里的营业时间/评分（有就记，没有就记“未核实”）。
   - **地址口径**：优先用 `maps_search_detail` 返回的 `address`；它为空时，才退回 `maps_around_search` 的 `address`。两者都为空 → 写“地址未提供（工具未返回）”。
4. 候选去重：同一 `id` 只保留一次；同名且位置相近的视为同一地点。**去重要在统计数量之前完成。**

> 为了提高“数据真实性”，`name`、`address` 一律**逐字使用工具返回的原文**，不翻译、不缩写、不补全“XX路XX号”。

### 第 3 步：逐条测真实步行路线

对每个有坐标的候选，调用：

```
maps_direction_walking(origin = 起点坐标, destination = 候选坐标)
```

从返回的 `route.paths` 里取：

- `paths[0].distance` → 步行距离（米）
- `paths[0].duration` → 步行耗时（秒）
- `paths[0].steps` 只用来提炼一句“怎么走”，**不要**把整串分步指令贴进回答。

**只能用 `maps_direction_walking` 给出步行时间。** 禁止：

- 用直线距离 ÷ 步行速度估算；
- 用 `maps_distance(type="3")` 的 `duration` 当作真实步行耗时写进表格；
- 用“大概 5 分钟”“步行约 500 米”这类没有工具支撑的表述。

对每个候选记下：`步行距离(米)`、`步行耗时(秒，原始值)`、`步行耗时(分钟，向上取整，仅用于展示)`。

**失败分支**：`isError: true`、或 `paths` 为空数组、或返回的 distance/duration 明显异常（如 2 公里只要 3 分钟），都算该点**路线规划失败**。默认处理是**排除该点**：不进推荐表，只在补充说明里列为“未采用：无真实步行数据”。仅当排除后达标数不足用户要求的数量时，才**额外**调用一次 `maps_distance(origins=起点坐标, destination=候选坐标, type="3")` 作为降级参考，并在表格里写成“约 N 分钟（maps_distance 降级，仅供参考）”、在补充说明里点名。

### 第 4 步：筛选 + 排序

1. **硬条件过滤**：用**未取整的秒数**与上限比较，即 `duration <= 时间上限（分钟）× 60`。超过的候选**一律不进推荐表**。超出上限但仍值得提示的，只能在表格外用一行写“<名称>：真实步行 X 分 Y 秒（超出上限）”，不写进 5 列表格。
2. **类型校验**：从 `type` 确认属于用户要的品类；明显不符（用户要咖啡馆，结果只有茶饮店、面包房）→ 标注“品类不完全匹配”，或在第 2 步补搜。
3. **排序**：
   - 用户说“优先近一点的” → 按**步行耗时升序**，耗时相同再看距离；
   - 用户给了“环境好/评分高/连锁品牌”等偏好 → 在**满足时间上限的集合内部**按该偏好排序，并把排序依据写清楚；
   - 用户没给偏好 → 按步行耗时升序（最近优先）。
4. **取数**：去重、类型校验、时间过滤都做完之后，剩下的才叫“达标集合”。取前 `min(达标数, 用户要的数量, 5)` 个；若用户要的数量大于 5，只给 5 个，并在补充说明写“已按单次上限只列 5 个”。达标数少于用户要求的数量时，**有多少给多少**，按第 6 节“达标数量不足”处理，**不要**拿超时地点凑数。

一个可复用的思路：先按耗时把全部候选排好序，再从头截取，这样“排序依据”和“表格里显示的数字”天然一致，AI 审核时也最容易对上。

### 第 5 步：返回推荐

严格按第 3 节的格式输出。输出的**每一个数字都必须能在本次工具返回里找到对应的值**；找不到就写“未核实 / 查询失败”，不要估算。

## 3. 回答格式

回答固定用下面四段，顺序不变。用 Markdown，表格优先。

### 3.1 开头一句：把需求复述成可校验的条件

```
起点：<查询命中名>（<城市·区>，坐标 <经度,纬度>）
需求：<类型>；单程步行 ≤ <N> 分钟；共 <K> 个（K = 表格实际行数，不足请求数时在此注明“请求 3 个，实际达标 2 个”）；排序依据：<...>
```

### 3.2 推荐表格（核心）

必须是一张 Markdown 表格，列固定为这 5 列（列名逐字照抄，不要增删、不要改名）：

| 地点名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|
| <地点名称，逐字来自工具返回的 name> | <地址，逐字来自 address> | 850 米 | 12 分钟 | 从起点步行 12 分钟（maps_direction_walking 实测），满足“15 分钟内”；类型为咖啡店，符合需求 |

列口径：

- **地点名称**：`maps_search_detail` / `maps_around_search` 返回的 `name` 原文。
- **地址**：按第 2 步的地址口径取原文；为空时写“地址未提供（工具未返回）”，**不要**自己拼。
- **步行距离**：`paths[0].distance` 的米数，不要换算成公里再四舍五入。
- **预计步行时间**：`paths[0].duration / 60` 向上取整，写“N 分钟”。若用了降级值，写“约 N 分钟（maps_distance 降级，仅供参考）”。
- **推荐理由**：最多两句，必须同时包含 (a) 与需求的对应关系（步行时间在上限内、品类相符、偏好命中），(b) 该地点可被工具证实的属性（`type`、营业时间、评分等，有则写、无则略），并以括号注明步行数据来自 `maps_direction_walking`。**不要**写“环境很好”“氛围温馨”“口碑极佳”这类工具没返回的形容词。

表格行数 = 实际达标数量。**不为了凑数把超时地点塞进表格。**

### 3.3 排序依据说明

用一两句话说明“为什么第 1 行排在前面”：

```
排序依据：按 maps_direction_walking 返回的单程步行耗时升序排列，第一行 12 分钟为达标候选中最近的一个。
```

若用户给了偏好（如“环境好的优先”），改写为偏好排序依据，并说明打破偏好时用的次要键（例如仍按步行耗时）。

若某个候选没有步行数据（见第 3 步的失败分支），它**不能**进入推荐表，只在补充说明里作为“未采用”列出。

### 3.4 补充说明（必写）

回答末尾用要点列出本次任务的边界与异常，**没有异常也要写“无”**：

- 未能满足的条件 / 建议放宽哪个条件；
- 有哪些信息“未核实”（如营业时间、评分、排队情况、人均消费、环境是否安静）；
- 工具调用异常（哪个工具、报什么错、如何降级）。

## 4. 一个完整的示例（仅示意格式与推理链，不代表真实数据）

> 用户：“我在北京西直门地铁站，想找一家咖啡店，步行不超过 15 分钟，推荐 3 家，优先近一点的。”

**第 1 步 · 定位起点**
- `maps_geo(address="北京西直门地铁站", city="北京")` → `return[0]` 里有 `location`（“经度,纬度”）、`city`、`district`、`level`。
- 记录：起点名 = “西直门地铁站”（命中名），起点坐标 = `return[0].location`。

**第 2 步 · 周边搜索**
- `maps_around_search(location=起点坐标, radius="2000", keywords="咖啡")` → 返回多个 POI（`id` / `name` / `address` / `typecode`）。
- 对每个 `id` 调 `maps_search_detail(id=...)` → 拿到各自的 `location`、`type`、`address`，以及 `biz_ext` 里的营业时间/评分（有则记）。

**第 3 步 · 真实路线**
- 对每个有坐标的候选调 `maps_direction_walking(origin=起点坐标, destination=候选坐标)` → 从 `route.paths[0]` 得到 `distance`(米)、`duration`(秒)。

**第 4 步 · 筛选排序**
- 先去重（同 `id`、或同名同址只留一条），再按 `type` 做类型校验；然后用 `duration`（秒）与 `15 × 60 = 900` 秒比较筛掉超时的；展示时 `duration/60` 向上取整；按耗时升序排，取前 `min(达标数, 3, 5) = 3` 个。

**第 5 步 · 输出**

起点：西直门地铁站（北京·西城区，坐标 <经度,纬度>）
需求：咖啡店；单程步行 ≤ 15 分钟；共 3 个；排序依据：步行时间升序（优先近一点的）

| 地点名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|
| （工具返回的 name） | （工具返回的 address） | 420 米 | 6 分钟 | 从起点步行 6 分钟（maps_direction_walking 实测）即达，是达标候选中最近的一个；`type` 为咖啡店，符合需求 |
| （同上） | （同上） | 880 米 | 11 分钟 | 步行 11 分钟（maps_direction_walking 实测），在上限内；`type` 为咖啡店，符合需求 |
| （同上） | （同上） | 1050 米 | 14 分钟 | 步行 14 分钟（maps_direction_walking 实测），在上限内；`type` 为咖啡店，符合需求 |

排序依据：按 `maps_direction_walking` 返回的单程步行耗时升序，第 1 行 6 分钟为达标候选中最近的一个。

补充说明：
- 未满足：无。三个候选全部满足“15 分钟内”与“咖啡店”两项。
- 未核实：营业时间、评分、人均消费、店内是否安静——工具未返回这些字段，一律标“未核实”。
- 工具异常：无。

> 示例里的店名、地址、距离、耗时都只是占位符。真实任务中**必须**替换成本次工具返回的值。

## 6. 异常处理与诚实标注（重要）

本 Skill 宁可回答“没找到”，也不允许补一个看起来合理的地点。以下情况**必须**如实写进“补充说明”，并且不允许用记忆或常识填补：

| 情况 | 判断依据 | 处理方式 |
|---|---|---|
| 起点定位失败 | `maps_geo` 的 `return` 为空数组或无 `return[0].location`，且 `maps_text_search` 无结果或其命中的 `maps_search_detail` 也无 `location` | 输出“未能把起点‘XX’解析为坐标（已依次尝试 maps_geo → maps_text_search → maps_search_detail，均未命中），因此无法给出基于真实步行路线的推荐”，逐个列出各工具的实际返回，再请用户补充“城市 + 更具体的起点（地铁站全称/地标名/门牌号）” |
| 周边搜索 0 结果 | `maps_around_search` 返回 `pois: []` | 换近义词或扩大半径补搜 1~2 次；仍为空则回答“在起点 <半径> 米范围内未检索到‘<关键词>’相关地点，建议放宽类型或扩大到更远范围”（`<半径>` 填**最后一次实际调用**的 radius 值） |
| 达标数量不足 | 去重、类型校验、时间过滤后的达标数少于用户要求的数量 | **有多少给多少**；再列出“若放宽到 <X> 分钟可增加的候选（及其真实步行时间）”。`<X>` 必须是某个未达标候选**真实**的 `duration` 向上取整后的分钟数，不能凭空写 |
| 路线规划失败 | `isError: true`、`paths` 为空数组，或 distance/duration 明显异常（如 2 公里 3 分钟） | 默认**排除**，只在补充说明里列“未采用”；仅当排除后达标数不足时，才降级用 `maps_distance(type="3")`，并在表格里标“约 N 分钟（maps_distance 降级，仅供参考）” |
| 地址为空 | `address` 为空数组/空字符串（两个工具都没有） | 写“地址未提供（工具未返回）” |
| 营业时间/评分缺失 | `biz_ext` 无相应字段 | 写“未核实”，**不要**写“营业中”“评分高”“很安静” |
| 排队长短、氛围、人均消费、是否有座位、是否宠物友好 | 所有工具都不返回 | 全部标“未核实”，不允许写任何猜测 |
| 需求自相矛盾 | 如“步行 3 分钟内 + 高评分 + 带儿童区” | 先如实检索并说明每个条件分别命中多少个；再**明确建议**放宽哪一条（例如把时限放宽到 15 分钟），让用户选择，不擅自替换需求 |

**禁止表述清单**（出现任意一条即视为编造）：没有工具支撑的“步行约 X 分钟”“距离大约 X 米”；工具未返回却写出的评分、营业状态、人均消费、环境评价；工具未返回却补全的门牌号；把某地点的名字改成用户更熟悉的叫法导致与地图不一致。
