# 技术使用记录

本文按"用到了什么、用在哪一步、怎么复核"记录三类技术的实际使用。所有记录都落在 seekdb 里
（表 `session_log`），可以用命令行或 HTTP 接口逐条查看；这里给的是本次提交时的实测数字。

## 1. MiniMax

| 项 | 内容 |
| --- | --- |
| 接入方式 | `MINIMAX_AGENT_OUTPUT`（人工粘贴通路）。同一条命令也支持 `MINIMAX_API_KEY`（ChatCompletion）与 `MINIMAX_AGENT_CMD`（命令行 Agent），见 `context/minimax.py` |
| 代码位置 | `context/minimax.py`（边界）、`context/operations.py::agent_prepare`（调用） |
| 输入 | `agent/artifacts/after/prompt.md`（12 409 字符）：任务说明 + 9 条规格 + 20 处代码来源 + 2 个既有测试文件 + 环境实测 |
| 输出 | `agent/artifacts/after/answer.md`，抽取出的补丁：`agent/artifacts/after/proposal.patch` |
| 校验 | 必须含 `diff --git`；用 `git apply --check` 在独立检出上试应用；统计改动文件与行数 |
| 应用 | `python run.py agent --step apply --worktree <seekdb 检出>`，产生的代码差异 `agent/code/minimax-change.diff` |
| 记录 | `session_log` 中 `role='minimax'` 共 2 条：1 条 `ok=false`（未提供回答，程序拒绝产出补丁）、1 条 `ok=true`（后端 manual，提示词 12 409 字符） |

复核：

```bash
python run.py state log | findstr minimax
```

## 2. seekdb / OceanBase

| 用途 | 实现 | 复核 |
| --- | --- | --- |
| 规格存储 | `spec`（9 行）、`spec_source`（20 处来源，13 个文件） | `python run.py specs`；`select spec_id, kind, state from spec` |
| 规格来源索引 | 导入时读 `SEEKDB_REPO` 下真实文件，校验符号位置，记录路径/符号/行号/原文 | `scripts/build_specs.py --force` 输出 |
| 任务状态 | `task_state`（当前版本）、`task_state_history`（每次保存一行） | `python run.py state history` |
| 使用记录 | `session_log`（24 行：guard 15、minimax 2、pytest 1 等） | `python run.py state log` |
| 验证执行 | guard 对运行中的 seekdb 逐条执行 SQL，记录错误码与返回行 | `python run.py guard --stage after` |
| 计量 | 导入数据集摘要 `dataset_sha256=c8b25025d2a97cb7` | `scripts/build_specs.py` 末行 |

数据库版本：`5.7.25-OceanBase seekdb-v1.4.0.0`，镜像 `oceanbase/seekdb:1.4.0-100000172026082615`。
两个账号分离权限：`minimax_ctx` 只读写 `minimax_sdd_ctx`，`minimax_test` 只操作 `minimax_scenario*`。

实际查询示例（本次运行）：

```
select 'spec', count(*) from spec                       -> 9
select 'spec_source', count(*) from spec_source         -> 20
select 'task_state_history', count(*) from task_state_history -> 9
select 'session_log', count(*) from session_log         -> 24
```

## 3. PowerContext

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| 任务状态保存 | `context/powercontext.py::save()` | 写 `task_state` 与 `task_state_history`；内容相同则版本号不变，不产生空版本 |
| 重启后读取 | `load()` | 只读数据库，没有本地状态文件（`powercontext.py` 里没有文件读写） |
| 再导入 | `import_state()` | 重新读取规格与检查结果，报告"保存后哪些规格内容变了" |
| 状态版本 | `history()` | 每次保存一个版本，评审可逐版核对 |
| 产物寻址 | `put_artifact()` / `get_artifact()` | 按 `任务/阶段/内容摘要` 寻址：MiniMax 补丁、最终代码差异 |
| 使用记录 | `log()` / `read_log()` | 与状态分离，写入即可读 |

本次实测（`logs/10-state-restart-import.log`、`logs/15-test-edit-takes-effect.log`）：

1. `agent --step prepare` 保存 `task-arr-element-dml@1`；
2. 进程结束，新进程执行 `state history`：读到 `@1`；
3. 新进程执行 `agent --step apply`：先 `import_state`，再用补丁修改检出，版本升到 `@2`；
4. 新进程执行 `state import`：报告 `revision: 2`、`specs_refreshed: 9`；
5. 修改 `ARR-006` 陈述后再次 `state import`：报告 `spec_content_changed_since_save = ['ARR-006']`，
   重建上下文后文本中出现新陈述；
6. 恢复陈述后 `state import`：报告不再变化，上下文回到原文。
