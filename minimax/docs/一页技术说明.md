# 一页技术说明

## 1. 它是做什么的

`minimax/` 是一个**面向软件持续演进的 SDD 上下文管理系统**。它把"这次任务要改什么、依据哪条规格、
依据哪段代码、改完必须守住什么"组织成可查询、可版本化、可复核的上下文，交给 MiniMax 参与真实代码修改。

本次任务：给 OceanBase seekdb（C++）的 ARRAY 列加按元素访问 `col[i]`，
涉及 `INSERT` / `UPDATE` / `DELETE` / `SELECT`，**不得改变**既有数组字面量与数组函数行为。

## 2. 模块结构

```
             ┌────────────────────────── seekdb / OceanBase ──────────────────────────┐
             │ spec · spec_source · test_case · task_state(历史) · artifact · session_log │
             └───▲────────────▲───────────────────▲──────────────────────▲──────────────┘
      规格导入   │     状态保存/恢复 │         实测结果写入 │               │ 补丁与代码差异
                 │            │                   │                      │
  scripts/       │   context/powercontext.py   context/guard.py      context/powercontext.py
  build_specs.py │            ▲                   │                      │
                 │            │                   │                      │
             context/build_context.py ────────────┘                      │
             （规格 + 代码来源哈希 + 既有测试 + 环境实测）                 │
                          │                                              │
                          ▼                                              │
                  context/minimax.py  ──►  MiniMax （api / cli / manual）┘
                          │                                              │
                          ▼                                              ▼
             run.py（CLI） / serve.py（HTTP） ─────────► context/operations.py（唯一实现）
```

所有读取都直连数据库：`context/build_context.py` 每次重建上下文都重新读规格、重新计算代码哈希，
`context/powercontext.py` 不含任何文件读写，所以**重启后读到的就是库里的内容**。

## 3. 上下文模块的接口

| 入口 | 形式 | 输入 | 输出 |
| --- | --- | --- | --- |
| `run.py context` | CLI | 任务/规格编号 | 文本或 JSON：适用规格、代码来源、既有测试、环境实测、上次结果 |
| `run.py agent` | CLI | `agent/instruction.md` | 提示词文件、MiniMax 回答、抽取后的补丁、保存的状态版本 |
| `run.py guard` | CLI | `baseline` / `after` | 每条检查的 pass/fail 与原因、JSON 报告 |
| `run.py state` | CLI | `show/history/import/save/mark/log` | 状态版本、导入报告、就绪度 |
| `serve.py` | HTTP | `/health` `/specs` `/context` `/tasks/{id}/state` `/tasks/{id}/import` `/ready` | 同上（供 MCP / Agent 插件接入） |

上下文正文由四段组成，每段都带来源：规格（含代码路径:行号与内容哈希）、必须继续通过的既有测试
（文件 + 哈希）、运行中服务的逐条实测、上次运行结果。角色划分：**seekdb** 存规格/来源/状态/记录，
**MiniMax** 只负责产出补丁，**PowerContext 层**负责把状态与证据按版本存起来供下次使用。

## 4. 规格怎么被"验证"

* **must-change**（ARR-001…005b）：guard 的验收用例在修改前必须失败、修改后必须通过；
* **must-keep**（ARR-006/007）：guard 的兼容用例比较错误码与返回行，修改前后都必须一致；
* **来源校验**：导入与构建上下文时重新读源码文件，符号漂移会警告而不是静默改号；
* **语法层**：`grammar_check/static_check.py` 直接读文法，判断是否存在 `column_ref '[' expr ']'` 产生式。

## 5. 本次的实际结果（不粉饰）

| 层 | 修改前 | 修改后 |
| --- | --- | --- |
| 语法层（ARR-005） | `element-access node: none` | `element-access node: T_OP_ARRAY_INDEX`（补丁生效） |
| 兼容层（ARR-006/007） | 2/2 pass | 2/2 pass |
| 服务层（ARR-001…004） | 0/4 pass | 仍 0/4（本机没有带补丁的 seekdb 构建） |
| 上下文模块自测 | — | 11 passed |

结论：系统完整跑通了"导入规格 → 组装上下文 → MiniMax 产出补丁 → 状态落库 → 重启后恢复 →
应用补丁 → 两层验证"的链路；**补丁本身只是解析层的第一步**，节点定义、解析路径、执行期实现、
回归结果都还没做，因此不能宣称功能完成。

## 6. 局限与下一步

1. 需要一台能 `./build.py build seekdb` 的 Linux 机器，编译补丁、补节点与解析路径、跑 mysqltest；
2. `array_index_probe.cpp` 届时可替换 `static_check.py`，直接以真实文法解析验证；
3. 把 MiniMax 接到 API/CLI 后，`MINIMAX-LOG.md` 中的粘贴通路可换成自动调用，其余流程不变；
4. 若要扩展到"跨会话多任务"，`task`/`task_state` 已按任务号建模，无需改表。
