# 技术使用记录：seekdb 与 PowerContext 到底各干了什么

> 本文所有数字与语句都来自本机实测，原始输出在 `logs/` 与 `docs/evidence/`。
> 测试环境：Windows 11 / Python 3.10.4 / Docker Desktop 4.82（Engine 29.6）/
> seekdb `5.7.25-OceanBase seekdb-v1.4.0.0`（镜像 `oceanbase/seekdb:1.4.0-100000172026082615`，`MODE=mini`）/
> PowerContext Server 1.5.0（loopback，access mode = disabled）/ 嵌入方式 `hash-ngram`（384 维，无第三方模型依赖）。

## 1. 分工一句话

| 技术 | 在项目里负责的事 | 论文里的「作用」 |
| --- | --- | --- |
| **seekdb** | 资料与复习题的**唯一存储**；把「全文 + 向量 + 结构化条件」做成**一条 SQL**，在库内完成两路候选生成与加权 RRF 融合；记录 `event_log` 审计日志 | 检索与排期都由数据库完成，应用层只发一条语句、只收一份排序结果 |
| **PowerContext** | 跨会话的**记忆服务**：检索偏好（课程范围 / 权重 / 标签 / 返回条数）、当前聚焦、薄弱点与掌握情况、会话交接 | 记忆在**下一次检索之前**被读取并转化为 SQL 的过滤条件与融合权重，实现「越用越懂你」 |

两边的数据互不重叠：seekdb 存的是「资料与排期」，PowerContext 存的是「关于这个人的偏好与状态」。

## 2. seekdb

### 2.1 表结构与索引

```sql
CREATE TABLE note (
  note_id     VARCHAR(64)  NOT NULL PRIMARY KEY,
  source_type VARCHAR(32)  NOT NULL,          -- note / paper / chat / meeting
  course      VARCHAR(128) NOT NULL DEFAULT '',   -- 结构化过滤条件
  topic       VARCHAR(128) NOT NULL DEFAULT '',
  tags        VARCHAR(512) NOT NULL DEFAULT '',
  title       VARCHAR(512) NOT NULL,
  body        TEXT         NOT NULL,
  embedding   VECTOR(384)  NOT NULL,
  created_at  DATETIME(6)  NOT NULL,
  FULLTEXT INDEX ft_note (title, body) WITH PARSER ik,
  VECTOR INDEX   vidx_note (embedding) WITH (distance=cosine, type=hnsw, lib=vsag)
) DEFAULT CHARSET = utf8mb4;
```

实测索引（`logs/04-indexes.log`，`SHOW INDEX FROM syncrecall.note`）：

| Key_name | Column_name | Index_type |
| --- | --- | --- |
| `PRIMARY` | `note_id` | BTREE |
| `ft_note` | `title` / `body` | **FULLTEXT**（`ik` 分词，`ik_mode=smart`） |
| `vidx_note` | `embedding` | **VECTOR**（HNSW，`M=16, EF_CONSTRUCTION=200, EF_SEARCH=64`） |

另外两张表：`review_card`（SM-2 排期：`ease` / `interval_days` / `repetitions` / `next_review_at`，
在 `next_review_at` 上有索引）和 `event_log`（每次检索、评分、偏好写入的审计行）。

### 2.2 一条 SQL 的混合检索

`src/syncrecall/search.py::build_hybrid_sql` 生成的结构（完整语句见 `docs/evidence/hybrid-sql.txt`）：

```sql
SELECT note_id, title, course, topic, source_type, tags,
       SUBSTRING(body, 1, 420) AS excerpt, fts_score, vec_score,
       ROUND(0.7 / (60 + COALESCE(fts_rank, 61)), 6)
     + ROUND(0.3 / (60 + COALESCE(vec_rank, 61)), 6) AS fused_score     -- 加权 RRF，库内计算
FROM (
  SELECT *, RANK() OVER (PARTITION BY fts_score IS NULL ORDER BY fts_score DESC) AS fts_rank,
            RANK() OVER (PARTITION BY vec_score IS NULL ORDER BY vec_score DESC) AS vec_rank
  FROM (
    SELECT note_id, title, course, topic, source_type, tags, body,
           MATCH(title, body) AGAINST ('Raft 不丢已提交 不丢已 丢已提 已提交' IN NATURAL LANGUAGE MODE) AS fts_score,
           (1 - cosine_distance(embedding, '[0.000000, … ]')) AS vec_score
    FROM note
    WHERE course IN ('分布式系统') AND source_type IN ('note')      -- 来自 PowerContext 的偏好
    ORDER BY cosine_distance(embedding, '[0.000000, … ]') APPROXIMATE
    LIMIT 60
  ) candidates
) ranked
WHERE (fts_score IS NOT NULL AND fts_score > 0) OR vec_score IS NOT NULL
ORDER BY fused_score DESC, title
LIMIT 6
```

要点：

- **两路候选在库内产生**：全文分支由 `MATCH ... AGAINST` 计算 `fts_score`，向量分支用
  `ORDER BY cosine_distance(...) APPROXIMATE` 走 HNSW 索引取近邻；应用层不取回中间结果。
- **结构化条件与向量检索同语句**：`WHERE course IN (...) ... ORDER BY cosine_distance(...) APPROXIMATE`
  被优化成带前置过滤的向量索引扫描（见 2.3）。
- **融合在库内完成**：`RANK()` 窗口函数给出两路名次，再按 `w/(k+rank)` 加和（`k=60`），权重来自记忆。
- **注入防护**：过滤值走参数绑定（`%s`），只有整数形式的权重与 LIMIT 内联；
  FTS 文本会去掉引号与反斜杠后再内联为字面量。

### 2.3 执行计划（实测）

`docs/evidence/explain-plan.txt`（`scripts/explain_plan.py` 生成）：

```
|7 |└─VECTOR INDEX ADAPTIVE SCAN (PRE-FILTER)|note|4|
      + MATCH(note.title, note.body) AGAINST('Raft 不丢已提交 ...')
      + cast(1, DOUBLE) - cosine_distance(note.embedding, cast('[...]'))
      + filter(...)  sort_keys(...)  order ... APPROXIMATE
```

即：**向量索引扫描**承担近邻检索，`course` 条件作为前置过滤（PRE-FILTER）下推，
全文分数在同一次扫描中计算 —— 佐证「一条语句、一个计划、两路分支」。

> 演进过程（也记录在 `logs/`）：最初只建了全文索引，向量分支退化成
> `TABLE FULL SCAN`；补建 HNSW 索引后变为 `VECTOR INDEX SCAN`。
> 另外 seekdb 要求带 `APPROXIMATE` 的 `ORDER BY` 必须是原始的
> `cosine_distance(...)` 表达式，写成 `ORDER BY vec_score DESC APPROXIMATE`
> 会报 `1235 Using vector index without vector_sort_expr is not supported`。

### 2.4 实测耗时

`event_log.elapsed_ms`（`docs/evidence/event-log.json`）在 21 条笔记上的混合检索：

| 操作 | 耗时 |
| --- | --- |
| seekdb 混合检索（一条 SQL） | 29–60 ms |
| 整个 `recall`（含 PowerContext 读写 + 本地嵌入） | 120–280 ms |

数据量只有 21 条，这个数字只用来证明链路通、耗时可接受，不能当作性能评测。

### 2.5 复习排期（seekdb 的第二个作用）

`review_card.next_review_at` 是**业务数据查询**：`/api/review` 按 `next_review_at <= now()` 与薄弱点
相关度排序取题；`/api/review/grade` 按 SM-2 更新 `ease` / `interval_days` / `repetitions` / `next_review_at`。
答完立刻能在 `event_log` 里看到 `grade_card` 记录（见 `logs/` 与界面右下角）。

## 3. PowerContext

### 3.1 接入方式

- 接入面：PowerContext 1.5.0 的 **HTTP API**（`POST /v1/scopes`、`POST /v1/memory/remember`、
  `POST /v1/memory/search`、`GET /v1/scopes/{id}/artifacts/atomic-memory`）。
  用 HTTP 而不是 Python SDK，是为了让评审只装 `powercontext[cli,server]` 就能跑（SDK 在 `client` extra 里）。
- 隔离：每个用户一个 **Scope**（`idempotency_key = syncrecall-scope-<user>`，重复创建返回同一 Scope）。
- 记忆类型：同一条 `kind` 下的多条 Memory，应用按 Artifact 的 `created_at` 取最新一条生效。

| kind | 写入时机 | 内容示例 | 被谁消费 |
| --- | --- | --- | --- |
| `profile` | 用户在「记住我」里保存偏好 | `检索偏好 {"courses":["分布式系统"],"source_types":["note","paper"],"keyword_weight":0.7,"vector_weight":0.3,"top_k":6,"tag":""}` | 下一次检索的 `WHERE` 与 RRF 权重 |
| `focus` | 用户切换「当前聚焦」 | `当前聚焦 分布式系统期末复习` | 复习队列默认课程 |
| `learning` | 每道题评分后 | `学习观察 {"course":"分布式系统","weak":["共识算法"],"strong":[]}` | 下一次复习计划把薄弱点提前 |
| `session` | 每次检索后自动写回 | `会话交接 11-04 14:49 检索「Raft …」，最相关的是《…》（分布式系统），共 6 条命中。` | 界面「上次会话」提示 |

### 3.2 一次检索里的记忆读写（可核对）

### 3.3 记忆改变了检索结果（实测前后对比）

`docs/evidence/before-after.json`，同一个问题「Raft 怎么保证不丢已提交的日志」：

| | PowerContext 里的偏好 | 命中（Top） | 所属课程 |
| --- | --- | --- | --- |
| 改动前 | 全部课程、全部来源，权重 0.6/0.4 | ①组会纪要 ②Raft 日志复制与提交规则 ③论文精读：Raft 与 Paxos | 分布式 + **数据库**混入 |
| 改动后 | 只看 `分布式系统`、来源 `note/paper`，权重 0.7/0.3 | ①Raft 日志复制与提交规则 ②论文精读：Raft 与 Paxos ③两阶段提交的阻塞点 ④Percolator 论文 ⑤Paxos 两个阶段 ⑥In Search of an Understandable Consensus Algorithm (Raft) | **全部为分布式系统**，且 Raft 原始论文进入结果 |

同一段代码、同一个问题，**只有 PowerContext 里的记忆变了**，检索范围与排序随之变化。
这一步是「记忆被保存并在后续使用中复用」的直接证据，也有对应集成测试
（`tests/test_integration.py::test_remembered_preference_changes_the_next_recall`）。

### 3.4 记忆如何影响复习（闭环）

1. 评分 `< 3`（忘了/勉强）：该题所属 `topic` 记入 `learning.weak`，写入 PowerContext；
2. 下次 `/api/review` 读取 `learning`，对 `question` 命中薄弱点的题给出更高权重（`weak_bonus`）；
3. 评分 `>= 3` 时移出 `weak` 并进入 `strong`。

## 4. 环境说明（Windows 上的一个坑）

PowerContext 的**嵌入式 seekdb** 存储依赖 `pylibseekdb`，其 wheel 目前只发布 Linux / macOS：

```
pylibseekdb<2,>=1.4.0.post2 ; (sys_platform == 'linux' or sys_platform == 'darwin') and extra == 'seekdb'
```

因此在 Windows 上：

- `POWERCONTEXT_SERVER_DATABASE_KIND=seekdb` 会在启动时报
  `MigrationError: backend_unavailable: The embedded seekdb binding is unavailable.`；
- `POWERCONTEXT_SERVER_DATABASE_KIND=oceanbase`（连 seekdb 服务端）这条路径被 PowerContext 1.5.0 的维护流程
  拒绝：`unsupported_target: OceanBase maintenance requires a MySQL user tenant.`（seekdb 1.4 不再暴露
  `ob_compatibility_mode`，也没有 `DBA_OB_TENANTS` 里的 `USER` 租户）。

本机的取法与建议：

1. 应用侧 seekdb（本文的检索与排期）在 Windows 上完全可用 —— 这就是 2.1 起的那个容器；
2. PowerContext Server 在 Windows 上用 SQLite 跑通全流程（本文所有记忆证据都是在这种配置下产生的，
   记忆**行为**与存储后端无关）；
3. 需要在评审机上完全对齐「PowerContext 也存 seekdb」时，把 PowerContext 放到 WSL2 / Linux 运行，
   用向导选嵌入式 seekdb 即可（`powercontext config init`，存储选 seekdb），应用只需改 `SR_POWERCONTEXT_URL`。

这个限制我们选择如实记录，而不是用文档粉饰。
